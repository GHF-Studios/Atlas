# Premium Docs Crosswalk — Intended Model, Later Direction, Current Evidence

**Snapshot checked:** local `Vapor-Client` at parent commit `a5c302a` (2026-10-23), nested `Vapor` at `5743065` (2026-10-23). The Premium Docs pages were clean in this checkout. This is a semantic cross-reference, not an approval to migrate or rewrite them. Source trees remain read-only.

## Finding in one sentence

The Premium Docs are a serious and unusually well-separated architecture corpus, but they are a dated proposed model that later implementation and owner decisions partly realized, partly narrowed, and partly superseded; because their own “stable semantics vs temporary reality” rule does not attach dated status to most claims, readers can mistake both old proposals and partially implemented mechanisms for current product contracts.

## How the corpus formed

The late-August USF glossary is a compact, unusually dense ontology snapshot: it separates simulation truth/authority from representation and runtime substrate, distinguishes spatial scale from temporal scale, and treats capabilities as explicitly provisioned invocation contracts rather than generic Rust/Rhai functions. It is high-value historical design evidence, not proof of the Engine's behavior or a Vapor-wide capability framework. See [USF Model glossary](</home/leslieghf/Vapor/Vapor-Client/Premium%20Docs/Glossary%20-%20USF%20Model.md>).

The September 4 [Rewrite Bootstrap](</home/leslieghf/Vapor/Vapor-Client/Premium%20Docs/Vapor%20Rewrite%20Bootstrap.md#L24>) reframed the existing Vapor implementation as useful evidence rather than trusted architectural authority, then proposed an end-to-end Phase 0: discover declarations, resolve/validate, realize Cargo, build, and run an Engine + Game + Mod + Packagepack. Its explicit “proved / did not prove” split is a strong epistemic pattern. The proof was a narrow hand-wired composition; it did not establish generic pack composition, arbitrary extension ABI, production identity, or release distribution. The September 9 [Progress and Roadmap](</home/leslieghf/Vapor/Vapor-Client/Premium%20Docs/Vapor%20Rewrite%20Progress%20And%20Roadmap.md#L112>) is a later living snapshot that itself warns that “PROVEN” names a mechanism, not final API, names, UX, or production readiness.

The September 9 [Premium Docs README](</home/leslieghf/Vapor/Vapor-Client/Premium%20Docs/README.md#L10>) then imposed a useful ownership discipline—one normative owner per concept—and split architecture, development, experience, migration, process, and reference. The split is real and useful; however, it left Bootstrap and Roadmap at the root while describing a `Process/` directory, which does not exist. A structural claim about the docs itself is therefore stale. The later books, planning corpus, decision ledgers, and owner clarifications add further layers; they do not automatically make every Premium Docs proposal current.

## Cross-document conflicts and why they matter

### 1. Ownership is explicit; temporal truth is not

The README correctly separates stable semantics, migration reality, process history and reference. Yet only the roadmap gives a compact claim-status taxonomy, and it is not consistently attached to downstream model prose. The result is **epistemic flattening**: old design, accepted owner decision, implementation, and verified end-to-end behavior are visually equivalent. The current books have improved central status/scope navigation but repeat product claims without local claim status. Fixing navigation alone will not resolve semantic contradictions; each concept needs a normative owner plus a dated authority/status and evidence pointer.

### 2. Packagepack / “Composition” / executable boundaries shifted

The older model separates authored Packagepack, resolved “Vapor App Composition,” and runtime instance. That distinction may still be useful internally as manifest, resolution snapshot, and process/run record. But the user explicitly rejected a second player-facing composition object: Packagepack is the playable selection; “composition” is informal. They also clarified packs as manifests and content as the real buildable/reusable payload, with only Packagepack additionally carrying the executable. These are not equivalent word changes: they alter catalog, Workshop, dependency, installation, locking, package-build, and user-selection identity. Current docs and code need one explicit model that can retain derived resolution state without promoting it into a second product object.

### 3. Role design mixes authorization, installed tools, and experience tiers

The old four-role ladder correctly says local capability is not authentication or remote authorization. Later user direction emphasizes three nested experience levels and clarified the Composer’s boundary: may use Cargo compositionally, but does not create Rust source. Current setup provisioning and workflow authorization still do not faithfully represent that boundary; publication authorization is a further independent service gap. A future model should distinguish: (a) user-facing workflow tier, (b) installed local tools/capabilities, and (c) identity/target authorization. These need mappings, not one overloaded `role` field.

### 4. Product topology changed after the SDK model

The old corpus anticipated one Client/Core and Launcher↔SDK Development Mode, and explicitly cautioned that executable count does not determine semantic boundaries. The later direction keeps the shared service/API but wants separate player Launcher, composition Studio, source/scripting IDE, plus Installer, chooser and CLI facades. This is a refinement consistent with shared semantics, not a contradiction of the service boundary. The correct invariant is shared domain/service ownership with separate product workflows; a monolithic GUI executable or one “SDK mode” should not be mistaken for that invariant.

### 5. Publication and distribution are distinct, but neither authority path is finished

The old source-publication model’s immutable semantic release and the Steam distribution model’s built executable are conceptually separable. Current Steam Workshop provides mutable item transport/discovery, while accepted user direction gives Registry catalog semantics and Identity authorization; current source does not yet join these into a canonical signed/releasable content record. The docs’ future Registry authority statements overstate current reality. The product needs a release identity that binds source version, target artifacts, dependencies, Workshop item/depot and policy authorization without conflating any one provider ID with the semantic release.

### 6. “Proven” is a mechanism claim, not a product promise

The roadmap states this caveat directly, but milestone labels and the historical-current-position block can still read like an active completion dashboard. The vertical slice and wheel game prove particular static realization/extension patterns; they do not prove generic content packs, full game distribution, cross-platform Workshop, broad dependency closure, or a ready user-facing ecosystem. This distinction should be mechanically visible whenever milestone state is reused.

### 7. Migration rigor was stronger than state freshness

The plan’s separation of provider identity, Vapor identity and local path, plus backups/known-good restoration, is excellent and should survive. But a live execution ledger with checked historical operations and stale blocking statuses is dangerous unless frozen as a dated snapshot or reconciled. Current repo names, consolidated product repositories and actual platform tooling have moved. Treating the old checklist as executable would repeat the very conflation the plan was designed to avoid.

## High-value ideas to preserve for the future architecture

- One semantic owner per concept; projections import rather than redefine.
- Separate semantic dependency meaning from Cargo/linker implementation.
- Separate source publication from built-App distribution.
- Keep local capability distinct from authentication and remote authorization.
- Keep context distinct from selection; filesystem cwd distinct from Vapor identity.
- Treat authored, derived, replaceable and recoverable state differently.
- Prefer explicit operations with readiness, preservation and diagnosable outcomes over a single opaque lifecycle.
- Mark historical proof narrowly and say what it did not prove.
- Preserve first-party and third-party product surfaces as clients of shared service semantics.

The decisive correction is that the Premium Docs model is neither wholly stale nor a current contract. Its graph/closure/Cargo-separation ideas survived; its **separate composition product identity** did not. Several graph semantics exist only as kind checks or derived string keys, and the rich constituency/artifact model has not been carried into the live types. Optional edges are omitted from default resolution and conflict declarations are represented, but this does not by itself implement the owner's mutually exclusive pack-path selection model. The owner-defined pack/content split, path/cardinality rules, explicit dependency meaning, and per-kind payload contract remain design decisions to reconcile before calling the content architecture settled.

This deep pass is source review only. It did not compile, run tests, exercise publication/install, or validate a generated executable.
