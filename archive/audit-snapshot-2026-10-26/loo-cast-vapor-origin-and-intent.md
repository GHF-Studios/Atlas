# Loo-Cast and Vapor: origin, intent, and causal history

This document reconstructs the project’s conceptual history across the reachable Loo-Cast and Vapor repository family. It is meant to connect the full [commit register](loo-cast-vapor-history-timeline.md), the [evidence atlas](vapor-ecosystem-evidence-atlas.md), the owner’s recorded design answers, and today’s code into one causal account. It distinguishes repository facts from remembered history and from my interpretation of what the project is trying to become.

The current objective reads this history from the **latest source snapshot backward**. The question is not only what ideas appeared first; it is what the current system now means, which prior choices accumulated into it, which later owner statements revised them, and which old ideas remain live pressure rather than doctrine. The newest code and design seams receive the deepest explanation. This narrative supplies causal context; the [current-state atlas](vapor-ecosystem-evidence-atlas.md) and [semantic review](loo-cast-vapor-semantic-diff-review.md) remain the evidence-ledgers for present implementation.

## How to read this reconstruction

**Evidence classes**

- **Observed:** directly supported by a commit, repository tree, current source, or dated owner-authored answer.
- **Remembered:** stated by the owner, but not independently recoverable from the examined Git history.
- **Interpretation:** a hypothesis about the reason behind a sequence. It is marked as such and is not doctrine.
- **Current implementation:** what the inspected code or repo structure implements now.
- **Owner direction:** a target the owner has explicitly articulated; it is not automatically implemented.

The work was deliberately examined in passes: repository and commit-map inventory; early Unity and modding clusters; engine extraction and Rust/prototype succession; the first named Vapor/Q&A sequence; then cross-repository product, distribution, service and authoring histories. The companion timeline contains 3,935 repository-commit entries across 20 related repository identities at the observed cutoff, including 2,350 in Loo-Cast-Legacy. Each entry belongs to a repository history; two identical seed commits are listed under both `Spacetime-Engine` and `Loo-Cast-Game`. Local checkouts expose 1,539 commits across 16 Git roots, but not the Legacy history. The index records timestamp, abbreviated identity, subject, and link where available. It does **not** claim a line-by-line semantic review of all 3,935 diffs. Individual changes were interpreted by combining chronology, milestone diffs, repository snapshots, design logs and owner statements. Generic commit messages (“WIP”, “stuff”, “cleanup”) are retained as evidence of activity but cannot carry a detailed semantic conclusion by themselves.

**Review depth follows current impact.** The early Unity and first Rust implementation periods are treated as a high-level record of major pivots, recurring problems, and representative evidence. Their code is not being atomized line by line. The most detailed source work is reserved for the current Vapor/content/service/product architecture and recent Loo-Cast integration, where choices still constrain the next design and can be corrected now.

The earliest recorded project origin is currently the owner’s recollection of early-to-mid 2021. The earliest verifiable Git root examined is June 7, 2022. The missing period is a real archival gap, not evidence that the project started in 2022. Exact pre-Git inspirations, early sketches, prototypes and naming history remain unknown unless recovered from local backups, old exports, or the owner’s memory.

## The origin problem, as far as the evidence allows

### 2021: a remembered beginning

**Remembered:** the owner says Loo-Cast began around early-to-mid 2021, before Git was used. Nothing in the repositories inspected proves what the first prototype looked like, which ideas appeared first, or when “Vapor” entered the vocabulary. It would be fiction to fill that gap with a confident origin story.

**Interpretation, confidence: medium.** The later history suggests the core desire was not simply “make a space game.” Loo-Cast repeatedly grows toward a game whose world and rules can expand beyond a fixed handcrafted implementation: authored data; reusable engine mechanisms; modding and extension; large spatial scales; and eventually a way to assemble and distribute chosen combinations. That interpretation fits recurring evidence from 2022 onward, but it cannot tell us which ambition came first or what personal experiences inspired it.

**Additional owner-origin evidence, but not proof of 2021 details:** a local, unversioned note titled `loo_cast_ai_integration_thoughts.txt` has filesystem modification time 2026-07-17; its creation date and history are unknown. It gives a later, direct first-person synthesis of Loo-Cast as several things at once: a gritty but hopeful societal commentary; a social parody and creative tool; a teaching/science-oriented universe; and a flexible, automatable game. The note names Half-Life 2, Factorio, Space Engineers, Minecraft, Star Trek, and Half-Life/Portal as inspirations, and connects complex NPC behavior to constrained AI integration. It then explicitly says that compressing this into one premise is difficult because the creative identity and the engine/modding architecture are entangled. This is stronger evidence of the owner’s later intended *combination* than the commit history can supply, but it does not establish that this combination existed in the same form in 2021. The note’s social hypothesis about why people behave differently is an authorial premise, not independently supported research and not treated here as a factual claim.

### June 2022: repository shell, then a complete-looking Unity game snapshot

The first reachable commit, [`29109ac3`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/29109ac3a84410c8e83c62a9c3a4b8c5e569e951), lands June 7, 2022. Its entire diff is `.gitignore`, a GPL-3.0 license, and a one-line README. Just under three hours later, [`922b9c84`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/922b9c844835d57a36ffb8ffb010e0f138762fa0), also titled “Initial commit,” introduces a 793-blob tree and 238,704 added lines. The changed-files list returned by GitHub’s commit/compare endpoints stopped at 300 entries; it was not the commit’s total. The complete tree contains three enabled build scenes, one template scene, 13 prefabs, 170 C# scripts and their metadata, plus materials, fonts, animation/controller assets, project settings, and collaboration/editor setup. The scripts cover the player and movement, enemies and bosses, health, stations, generators/spawners, targeting, weapons/projectiles, experience/currency, attributes/stats, UI, and shared managers/utilities. This is already a broad Unity game implementation, not merely an asset import or partial source sample. The tree alone still cannot prove that it opened, built, or played correctly in Unity.

On June 13, [`9d78bbfb`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/9d78bbfbf70bcf2e6b70e3385c32d5286689c507), “Actual initial commit,” changes nine files: it removes a large unused `Quad` object from `Game.unity`, adds a Bloom global-volume profile, updates that scene’s reference and editor layout/recents. Its label is misleading if read as the first code import; the parent graph and patch prove otherwise. The earlier `922b9c84` is the first large Unity project diff.

**Startup path verified from the imported source:** `ApplicationManager.Start()` calls its initializer; that marks the manager persistent, initializes the attribute/stat registry, initializes the initialization-scene manager, and requests `MainMenu` through the loading-screen path. The later `GameSceneManager.Start()` initializes the world-space canvas, background, sound, Player, screen shake, game canvas, generators, and then resumes gameplay. The custom `ExtendedMonoBehaviour` base is present in the tree and centralizes pause-aware `Update`/`FixedUpdate` hooks alongside uninterrupted cycles. This closes the earlier apparent “no bootstrap” and missing-base gaps at source level. It does not prove Unity lifecycle ordering, successful scene loading, or runtime correctness; no historical editor/build/run was performed.

**Serialized source-reference cross-check:** across the four scenes and thirteen prefabs, 194 script-component references use 73 distinct GUIDs. Fifty-seven of those GUIDs resolve to tracked project C# metadata. The remaining 16 are not evidence of missing game source by themselves: Unity packages and built-in/editor components also appear in serialized scenes, and the complete project manifest includes UGUI, TextMeshPro, URP, VFX Graph, and other Unity packages. Per-scene resolution is similarly stronger than the capped initial scan suggested: Game resolves 30 of 45 unique script GUIDs to project scripts, Initialization resolves 4 of 9, and the remainder require package/built-in classification. The scene graph and project source are substantially connected, but this Git-only count is not a Unity missing-script check.

### 2022: make game data editable, then make the game larger

The first weeks after the imported snapshot shift from an already sizeable hard-coded game toward data-driven authoring. June 13’s [`77c0094d`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/77c0094d1eda7e17abf3f206748dcd86937c4fe4) adds ScriptableObject-backed float/int variables and constant-or-variable references, plus a ScriptableObject event/listener pattern. It also contains a concrete early defect: `IntReference.Variable` is typed as `IntReference` rather than `IntVariable`; the June 16 modularization diff later corrects it while moving these classes into `LooCast.Data`.

On June 16, [`29b1b2e4`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/29b1b2e4961f293ef8223496ec26044c821313ce) makes the shift broad: 309 changed file blobs, including 43 C# paths and a large serialized asset/metadata graph, introducing typed data assets for weapons and stations, per-value reference assets, editor drawers, and runtime sets. Weapon code now reads fields from `WeaponData` ScriptableObjects instead of receiving many primitive parameters/defaults; station registration moves from a static list into an authored `StationRuntimeSet`. This increases inspector-authored reuse, but also couples serialized assets and runtime scripts through Unity references and `Resources` paths. Some stat formula code uses `System.Data.DataTable.Compute` for simple arithmetic; at least one edited stat contains an unreachable duplicate `return`. This is evidence that the new authoring model brought both flexibility and avoidable complexity/defects, not proof that every asset or formula was broken.

The following weeks repeatedly develop the model, prepare Attribute/Stat data integration, revise ValueVariable types, wire levels to events, and correct/revert confusion. August adds custom PropertyDrawers and inspectors for variables and computed values, then the author explicitly restores a data backup because “most of the Game Scene works again.” Persistence is subsequently tried. This is stronger evidence of integration cost than the earlier broad wording: the migration changed health/runtime-data shapes, component lifecycle and many serialized assets in parallel, and one source-level follow-up fixes UI access to wrapped values. September then adds inventory, missions and procedural-world tools while those data/editor conventions are still moving; the mission-task system is explicitly shelved to start world generation. The sequence exposes a durable tension: the author wants data to be reusable and editor-friendly, while the representation, serialized asset graph and runtime integration are themselves difficult enough to destabilize the game.

At the same time, the project gets a first Steam build in August and develops into asteroids, inventory, items/upgrades, stations, missions, targeting, AI, and world generation. This is not yet a mod platform: the work is inside a Unity game project and its editor. But the coupling between authored definitions, tools, runtime and distribution is already present in miniature. A compelling editor alone is not the goal; it should make real game content possible.

Late 2022’s world-generation and save/load exploration is followed by an explicit revert/removal of the persistence work. This is an early warning against reading a commit as a durable feature: some efforts were experiments that were backed out, and commit volume overstates the amount of stable product behavior.

### January 2023: “modding” becomes an explicit model

The January history contains three unusually meaningful clusters amid many implementation commits:

- [`d62a53a4`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/d62a53a4e4dcad27f7bd3161b87043fc15848d8e), “WIP Modding Framework,” starts an explicit mod framework.
- [`9d31582b`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/9d31582be469d746d5a92d615d5d14688c2a0ad1), “Added Modding Framework Plan,” frames the work through a planned Grand Unified Data System (GUDS).
- [`fad054e4`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/fad054e4a202d691042c2f9f3730f3de38be4852), “WIP Identifier System,” pursues identifiers and APIs as separate machinery.

The initial code/plan blend is revealing: mod manifests, IDs, module loading, version/dependency/conflict concerns and gameplay-facing data are all being approached in the same project. **Interpretation, confidence: high for the problem pressure, medium for the motive:** the first modding idea is not just “let users add files”; it is to make extension legible and composable enough that the game can load defined modules and eventually reason about their relationships. The early framework still mixes responsibilities and does not prove that a stable compatibility or package model existed.

### February–December 2023: build the engine chair while sitting on it

On February 3, [`2176ae0a`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/2176ae0af4cd8b2e8cc21ac6d1139499cab569ce) moves the codebase into “Base Mod.” Its message—“Now I gotta weave the threads back together, while building the chair I am sitting on”—is unusually direct evidence of the development experience: the foundational mod/framework is not a finished platform under a game; it is being constructed while it is needed. This helps explain why the code later shows both ambitious reusable abstractions and periods of tightly coupled experimental work.

In April, [`941b2010`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/941b2010c1d11ec1620bfb7ade12c14c3a6fd3b5) explicitly removes the existing game code and assets to create a starting point for engine work without legacy interference. This is a substantial conceptual break, not a routine cleanup. The author is willing to sacrifice a working game substrate to give engine construction its own space. The consequence is double-edged: engine concerns become more visible and less entangled with old gameplay, but the game’s concrete demands can no longer automatically discipline the engine design. Reuse can become an end in itself unless gameplay returns as a real consumer.

The remainder of 2023 tries multiple answers for the engine’s internal model: hierarchy and scene structures, a custom Entity-Logic-Data arrangement, then ECS in [`87b8a852`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/87b8a8529319076113fc9a083f890ef84e61300b). Universe-scale coordinates, chunking and serialization become major work. In September, the earliest direct written USF seed found so far appears as a 74-line prompt backup: it connects Phenomena, scale-specific ECS models, event durations, contextual dependencies, detail/zone maps, scale transitions and chunk observation. That is a meaningful conceptual ancestor, but a prompt is not a finalized model or working runtime. The code experiment beside it is also revealing: a worker thread is added for chunk generation, but the live observer still generates and loads synchronously; later worker revisions advance lifecycle states without performing the named work. The concept and implementation are both real, but they are not yet a coherent system. An explicit bug-hunting sequence temporarily removes much of a tangled system to isolate a fatal issue; the author’s commit messages describe the code as interconnected and the serializer as needing a major redesign. That is firsthand evidence for a recurring code-quality concern: architecture that technically supports a desired feature can become so interdependent that debugging requires structural reduction. See the [September source review](loo-cast-vapor-semantic-diff-review.md#september-2023-asynchronous-chunk-generation-and-a-written-usf-concept).

#### Close reading: what the first written USF seed commits to—and what it leaves tangled

The September 9 prompt backup is unusually dense: it makes world ontology, simulation scheduling, content detail, storage, and save compatibility one proposal. The following are **claims in that note**, not claims that the Rust prototype implemented them.

| Seed commitment | Why it matters | Ambiguity or consequence visible in the note |
|---|---|---|
| A *Phenomenon* is both an observed experience and “essentially a unique identifier”; its scale-specific *Phenomenon Model* is both one ECS entity and an archetype/component collection. | Identity, the thing observed, runtime instance, and structural schema are introduced together. | These are different semantic objects. The note does not yet say which identity survives replacement, how one phenomenon’s per-scale models link, or whether “archetype” means immutable schema versus live entity. |
| Models are typed Localized/Aerial; state must match the model type; events have four instantaneous/continuous × localized/aerial forms. | Spatial extent and duration become first-class rules of event delivery, not only rendering details. | The note does not define event ownership, duration clock, collision/overlap, ordering, or how transitions between event categories work. |
| Scales differ by 10×; the active scale is direct simulation, higher scales indirect; marker components gate scale-specific systems. | This is an early scale-sliced ECS schedule: scale determines both representation/detail and which systems execute. | It fixes a ratio and puts scale authority in marker membership before defining who changes that membership or reconciles time and state across scales. |
| Context dependencies form a single-parent/multiple-child acyclic tree; yet a model may depend on another model at the same scale or different positions in the scale hierarchy. | Context is meant to connect cross-scale representations while forbidding loops. | “Context,” “parent,” and “dependency” may not be the same edge. The note lists multiple allowed contextual targets without specifying how they still yield one tree or what changing a context does to descendants. |
| A model’s 2D Data Point Matrix carries probabilities and metrics; state changes update it and propagate upward immediately. Zone Lookup Maps partition all metric combinations; scale-specific Constraint-Template-Sets drive modified WFC. | The proposal joins coarse-to-fine emergence, probabilistic fields, classification, and constrained placement into one generation pipeline. | Completeness of an N-dimensional zone partition is a strong authoring invariant, but metric domains, overlap/gaps, update budgets, determinism and consistency after local mutation are unspecified. “Immediate” propagation also has no scheduling or batching policy. |
| Chunks define a fixed viewing radius; lower scales are not loaded and higher scales exist only as contexts. Foundational rules are immutable per save; changing them requires a new save. A database (possibly MongoDB) is proposed. | Runtime residency, persistence, and rule-version compatibility are already connected to the scale model. | The note does not distinguish generated, persisted, resident and simulated data, nor specify migration or how a new save inherits content. The database is a candidate, not a selected or implemented dependency. |

**Interpretation, confidence: high that the central problem was already multi-scale representation and detail selection; medium that the note intended a single unified runtime architecture.** It describes an ambitious closed loop from identity → scale-specific model → state/events → cross-scale data → classified zones → generated detail → chunk residency → save-bound rules. But several words stand in for multiple layers of authority. This is an important precursor to later USF work precisely because it reveals the knot early; it should not be retroactively treated as a settled contract for current USF.

The June typed-path work is a useful concrete example of the difference between an architectural direction and a delivered foundation. `FilePath`, `FolderPath` and `ObjectPath` are given combination, ancestry and naming APIs, but their new non-void methods are empty and duplicate existing typed equality methods, making that snapshot uncompilable as C#. The parsers also contradict their own relative/absolute representation: the folder root parses as relative and serializes to an empty string, while absolute folder paths retain their leading empty segment and serialize with an extra slash; nested absolute files inherit malformed parent spelling. ObjectPath reverses the leading-slash test. This supports a cautious reading of the period: the hierarchy/file-system direction was being explored seriously, but the first API shape had outrun its implementation and invariant design. These are source-derived findings; this historical review did not build that Unity revision.

The July ECS replacement clarifies a second lasting tension: semantic ownership is made explicit, but the framework also takes on rules that a mature runtime normally supplies. Components are keyed only by exact concrete type, which imposes one-instance-per-type cardinality; constructing a duplicate occurs before the duplicate check; destroying a component clears the identifier used by its equality and hash code. This is evidence of experimentation with stronger object semantics, not evidence that the custom ECS was already a safer or more capable replacement for Unity’s entity/component machinery. The next lifecycle and serializer changes make this ownership choice broader rather than resolving it immediately.

In November, a temporary Rust-source reorganization makes semantic placement explicit through manual sections for imports, statics, constants, types, enums, structs, implementations and module functions. The accompanying commit message says the experience felt good, but admits subcategories cannot easily be enforced and leaves them as undocumented “implicit knowledge.” This is a small but unusually direct ancestor of the later Vapor IDE ambition: the desired code model is meant to make semantic categories visible and navigable, while the old approach stopped at comments and convention. That is a thematic recurrence, not evidence that the 2026 IDE design was already planned in 2023.

The scripting path also has an early false start. A bespoke command system appears in August and is removed in [`94fe0fd5`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/94fe0fd59366ca2bce312e9a7c04e03a1a55176e) in favor of Lua, followed by Lua console and mapping work. This does not establish a direct path to current Rhai. It does establish that extensible runtime behavior and an in-game developer interface have been recurring questions, with concrete host integration rather than a desire for a detached text-only script editor. The later August 21 reset is equally important: a Unity mod-framework branch was merged into the repository, then the next root snapshot deleted its project tree and introduced a separate Bevy arcade prototype. The manifest and module vocabulary prove that this particular framework was attempted; tree comparison proves its implementation was not carried into the Rust snapshot. That sharp reversal argues against narrating the later Rust/Vapor architecture as a smooth implementation of the 2023 framework, while leaving the recurring desire for modular and authored behavior visible as a possible conceptual through-line.

**Causal reading of 2022–23:** data authoring led toward modularity; modularity raised identity and extension questions; those questions pulled the game toward a base mod/engine; engine construction then exposed scale, lifecycle, serialization and scripting problems; repeated coupling and rewrite pressure made a more principled host/tooling boundary attractive. This is a plausible chain supported by ordering and commit content. It is not proof that each step was consciously planned as a single long-term roadmap.

## First synthesis: what the early history says, and does not say

### Strongly supported

1. **Loo-Cast became an engine/content-authoring problem as well as a game.** This shift is evidenced by the 2023 Base Mod move and explicit gameplay-code wipe.
2. **Modding was treated as a structural concern.** IDs, modules, dependencies and conflicts emerge early; they are not an afterthought added only after Vapor.
3. **The author repeatedly sought mechanisms that make content extensible through tools.** ScriptableObjects, custom drawers, data modularization, editor tooling, command consoles and scripting all point in this direction.
4. **The cost of over-coupled implementation was experienced directly.** The 2023 serialization/debugging records describe removing large quantities of code to isolate a fault.
5. **Many implementation paths were exploratory and reversible.** Save/load, hierarchy/data models, command systems and scripting choices changed. The correct historical unit is often a problem being revisited, not a feature surviving unchanged.

### Still not established

- The original 2021 idea, inspirations, prototype, and order of ambitions.
- Whether the first modding vision was mainly user creativity, engine reuse, or a way to make the creator’s own work easier.
- Which Unity-era systems were consciously meant to survive the engine rewrite.
- That current USF, Rhai, Vapor content kinds, Workshop semantics or static-link composition were already specified in 2022–23.
- That the new Vapor system is a direct code continuation of the Unity mod framework or Lua experiments.

## Working causal model (to be revised as later history is examined)

```text
2022 game needs authorable data and useful tools
        ↓
modular data and extension force questions of identity, loading and compatibility
        ↓
Base Mod / engine extraction separates reusable machinery from Loo-Cast gameplay
        ↓
engine experiments expose scale, lifecycle, persistence, scripting and coupling limits
        ↓
2024–25 Rust/Bevy prototypes continue the engine problem, while mod/content semantics remain unsettled
        ↓
Jan–Mar 2026 prototypes Rhai hooks, temporary ECS access and typed USF content against Rust-owned operations
        ↓
Apr–Jun 2026 owner answers correct prototype-derived assumptions; design intent, implementation evidence and legacy signals gain separate authority
        ↓
Named Vapor reframes the problem at ecosystem scale: define, build, distribute, install, compose and launch content
```

The arrows mean “the next period can be understood partly as a response to pressure in the previous one,” not “the later solution was already intended.”

## 2024–June 2026: the engine line continues, and its vocabulary gets a governance layer

### January–April 2024: Rust separation does not remove structural friction

January 2024 contains a meaningful transition: Engine and BaseMod are made separate Rust crates in [`9028dcea`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/9028dcea63646f6588b932304545f246b8267f33). The project is no longer only about reshaping Unity systems; it is now exploring Rust compilation, kernels, build scripts, management, macros, modules, and Lua integration. But the commit sequence itself carries the difficulty: “dribbled” compiler errors, confusion, a build script the author calls useless and potentially harmful, linker trouble severe enough to make abandoning the work sound attractive, and rapid reverts of management-framework changes. The distinction Engine/BaseMod is being expressed as crates, but expressing it is not yet the same as making it easy to build or consume. The January 16 follow-up adds the dependency edge while commenting out the existing player/local chunk-operation paths to get past compile errors; the observer still records those chunk positions as viewed even though no lifecycle requests are submitted. The intended split initially costs working behavior instead of replacing it. This is one of the clearest early records of the project’s recurring gap between a meaningful boundary and a complete integration path.

Two later comments are unusually instructive for the eventual Vapor design. A January naming change says “Savegame” should be one combined entity, not a “Save Game” fusion of separate concepts. In February, a commit says command structures are essential to a project of this size. Together they suggest an author who cares deeply about semantic boundaries and naming because they change how a system is understood—not merely about packaging code into folders. These are small commit-level signals, not enough to infer a complete doctrine.

March–April commit subjects cluster around command frameworks, registries/assets/files, macro frameworks, and a kernel framework. The repetition is useful: the engine is seeking a stable internal substrate and a way to declare / connect behavior, but the history still shows repeated work-in-progress rather than a settled consumer contract. February provides a concrete integration test of that interpretation: the command API is called essential, but a player-startup revision removes local-universe registration, changes a processor signature without updating its call site or body, and retains direct GlobalUniverse calls. These are pressure signals, not proof of a durable architecture. The March 21 asset/file experiment is a second concrete probe: typed module names and a derive-macro import appear, but the macro is absent at that commit, the asset methods are empty, and command closures do not return the declared output. Both tracks expose the same missing piece: a complete host-owned lifecycle from declaration through execution/result. The timeline now records source-level evidence for selected diffs; it does not claim every historical commit has received a line-by-line review.

The May reset removes both the new Rust authoring framework and the preceding game runtime: the commit pair deletes the BaseMod/macro crates and design notes, plus the Engine’s background, camera, game, player, savegame and UI modules. `main.rs` is reduced to a default Bevy app; Mk0 then starts a separate chunk-streaming sandbox. This is not a smooth framework-to-prototype migration—the working tree explicitly withdraws one broad direction before testing another.

### May 2024–early 2025: Mk prototypes are a sequence of resets, not releases

On May 2, 2024, a cleanup is immediately followed by Prototype Mk0, then Mk1, Mk2, Mk3, Mk4 and the long Mk5 line. Later Mk6 and Mk7 show up in early 2025, with reverts, reapplications, bug-driven changes, and explicit transition notes. Mk8 and Mk9 follow. The commit index contains hundreds of checkpoint commits whose subjects are nearly identical (“WIP Prototype Mk5”, and later Mk6/Mk7/Mk9). Those commits are still useful: they show sustained hands-on iteration and prototype succession. But they do not identify every design detail by title, so this account avoids inventing fine-grained semantics from WIP names.

**Interpretation, high confidence:** `MkN` is an explicit mechanism for allowing a new implementation attempt to replace the current one without pretending it is a smooth, production-compatible version. It gives the owner permission to discard internals while preserving selected learning. That matches the pattern already seen in 2023’s engine extraction and later in Vapor’s rewrite thesis. It also creates a recurring risk: if the project advances by resetting prototypes, important ideas and user-facing requirements can survive only in memory, old docs, and conversation logs unless a deliberate migration captures them.

The May–June 2024 prototype also sharpens a specific recurring boundary: registry-retained world-object identity versus temporary ECS realization. Custom IDs, registries, loaded-entity sets and lifecycle events are attempts to express that split, but the code still coordinates them manually; the June source notes silent upgrades and identifies deferred-command timing as the cause. The attempted entity-to-actor conversion is itself unwired in its plugin snapshot, and its deferred handler's request/chunk filtering is internally inconsistent. A week later, the replacement upgrade path is wired, but a parameter rename makes single-ID unregister clear the entire registered-entity set; the new `EntityReference` is only an alias for Bevy `Entity`. Its serialized-chunk map is process memory, not demonstrated durable storage. The proposed stage and event graph are local experiments, not a general operation framework. This is relevant ancestry for later USF and lifecycle discussions, but no direct API continuity is established. See the [patch-level May–June review](loo-cast-vapor-semantic-diff-review.md#may-2024-the-kernelmacro-experiment-is-discarded-chunk-streaming-becomes-a-new-engine-prototype).

Mk0's PowerShell script clears only the `build\debug` staging/output directory, not Cargo's compiler cache. See the [source-pinned comparison](loo-cast-vapor-semantic-diff-review.md#focused-source-check-mk0-and-mk1-chunk-residency).

In parallel, August sketches Rust primitives composed by Lua and a typed Rust `Operation` protocol; the latter can directly mutate `World`, and async replies still need an external queue runner. The concrete Lua entry script defines `initialize_ops_module()` but invokes `ops:defineComposite(...)` before calling it, so evaluating the file as written reaches a nil `ops`; the Rust change adds `mlua` but no script loader or primitive-registration path. This is evidence that the desired host/script relationship was being explored before the later Rhai work, but it does not establish direct implementation lineage or an already-safe capability boundary. See the [July–August patch review](loo-cast-vapor-semantic-diff-review.md#july-2024-queued-lifecycle-work-moves-into-registries-chunk-allocation-and-entity-requests-are-reworked).

September makes the operation model more explicit—generic IDs, typed arguments/results, a global queue, callbacks and a process-global type registry—while introducing equally important counterevidence: operations are still `todo!()` or incomplete, executor code gets unrestricted mutable `World`, component hooks can alter identity as a side effect, and a module migration is reverted and attempted again. The chunk-save/load slice stores RON only in a process-global map; exact source shows success callbacks missing from the new load/save paths, “unsave” leaving the stored record behind, and unload holding the registry lock across hook-triggering despawns. The latter is a source-visible self-deadlock path, not a reproduced hang. This resembles later goals at the level of problem shape (host-owned operations composed by authored behavior), but it is not the same system and does not show a safe, finished substrate. See the [September patch review](loo-cast-vapor-semantic-diff-review.md#september-2024-generic-operations-meet-lifecycle-hooks-serialization-and-async-calls).

October–November then imagine a single path-addressed graph owning types, data registries, commands, operations and lifecycle phases, with distinct static and runtime identity. That graph is a strong conceptual precursor to later capability-graph discussion, but source review finds empty/incomplete lock rules, unfinished path access, placeholder phase bindings and renewed coexistence of queue and hierarchy. The November 30 pivot replaces lifecycle phases with insertion/removal hooks but leaves consumers implementing methods removed from the trait, making that snapshot source-inconsistent. It shows both the ambition of a unified semantic substrate and the risk of treating one graph as a safety boundary before its access, execution, and migration rules are real. See the [October–November review](loo-cast-vapor-semantic-diff-review.md#october-2024-a-typed-locking-hierarchy-replaces-the-global-operation-queue).

The exact December engine tree inspected does not wire a Lua loader or the task-operation bridge into the active plugin path; several engine modules are commented out, while the `.lua` files use Rust-like loop/range syntax and even `else then`, which is not Lua 5.4 syntax. That makes this a disconnected language/runtime experiment in the reviewed snapshot, not demonstrated working scripting. A state manager, global maps, component hooks, retry queue and then an action buffer each try to own transitions; the retry loop can spin, and later action stages still have no completed public result path. The lasting historical signal is the repeated demand for reusable, composable work with clear ownership—not continuity of any operation/lock/script implementation. See the [December–January review](loo-cast-vapor-semantic-diff-review.md#december-2024-chunk-streaming-returns-lua-tasks-and-ownership-retries-are-prototyped).

The generated surface claims typed stage IO, but the runtime erases values through `Any`; an exact February snapshot discards stage outputs, can resubmit an async stage every frame before its first completion, and does not match completion events to their declared stage index. Reviewed conversions later use generated `unsafe`, while completion/wait/failure channels and render-world extraction are repeatedly rewritten. This is a closer technical precursor to later codegen and temporal-stage discussions than the 2024 command macro, but it remains a separate, partially wired workflow system, not a surviving implementation of Rhai metaprogramming. See the [February–March 2025 review](loo-cast-vapor-semantic-diff-review.md#loo-cast-legacy--2025-02-staged-actions-mutate-into-workflows-then-into-a-macro-language).

April extends that same 2025 workflow experiment rather than establishing a new language or runtime. It makes setup, retained state, waiting, completion and failure explicit across generated stage handlers; introduces bounded one-item channels and receive-before-poll schedule edges; and moves workflow topology toward a generated registry. The cost is a broad matrix of generated cases, process-global one-shot channel initialization, panic-based erased-type recovery, and mutable resumption through registered workflow definitions rather than clearly per-call instances. Render-while state is temporarily split from a shared extraction resource and fused back after polling, making scheduler order part of correctness. These patches show an attempt to turn staged asynchronous work into an authored, declarative host system. They do not prove it was safe for concurrent invocations or that the generated path compiled and ran. This is a recurring design pressure relevant to the later Rhai hook/schedule discussion, not a direct code lineage. See the [April 2025 review](loo-cast-vapor-semantic-diff-review.md#loo-cast-legacy--2025-04-workflow-generation-absorbs-stage-ownership-dispatch-and-scheduling).

Queue items are removed before their workflow outcome is known, coarse per-system handles serialize new batches, and retry/error behavior is often panic-based. A parallel custom log viewer starts to model trace hierarchy and source locations, then forks into an unfinished duplicate store. See the [May](loo-cast-vapor-semantic-diff-review.md#loo-cast-legacy--2025-05-workflow-staging-is-redirected-toward-chunk-actions-and-captured-composite-work) and [June](loo-cast-vapor-semantic-diff-review.md#loo-cast-legacy--2025-06-chunk-intents-split-into-buffers-an-unfinished-log-viewer-is-prototyped-twice) reviews.

The rapid reversal matters: infrastructure was briefly gated by game pause, and a central run condition existed before it enforced its name. Vendoring the event crate asserts ownership while deleting its tests removes evidence of the contract. The transition state is revised repeatedly, and conversion still passes large integer coordinates through `f32`, so hierarchical labels do not yet deliver bounded precision. Some boundary operations panic or remain TODO, while origin rebasing arrives only at month end. This is a meaningful antecedent to the later scale-axis discussion, but the evidence remains spatial: no coupled temporal scale or relativistic motion contract is present here. ### September 2025–June 2026: modding plus USF, then deliberate archaeology

January 2026 is the first reviewed Rhai capability spike in this chronology. It puts named startup hooks beside a Rust-built reflection/API registry and explores giving scripts short-lived access to Bevy entities and world operations. The code makes an important conceptual shape concrete: host code opens an access window for a script call and tries to close it afterward. But the implementation transmutes Rust borrows to `'static`, relies on custom shared handles and reference-count checks, and can panic when teardown assumptions fail. It therefore exposes the exact problem the later “retain data, reacquire access” discussion is trying to solve, while also showing why the lifetime boundary cannot be treated as solved. Type reflection is hand-modeled alongside Rust and then expanded into proc-macro/inventory and dynamic-trait experiments; those declarations are not yet guaranteed to match compiled types. The accompanying build script still invokes host Cargo and deletes a profile output directory, so this scripting direction is not yet integrated with Vapor-owned build/toolchain policy. This is an intellectual precursor, not direct continuity with the later design, and not evidence of a production-safe runtime. See the [January 2026 hunk review](loo-cast-vapor-semantic-diff-review.md#loo-cast-legacy--2026-01-rhai-capability-experiments-and-reflection-substrate).

February 2026 is a useful counterexample to reading rapid refactors as convergence. Bevy’s direct 0.16→0.18 jump forces dependency/API choices, including dropping integrations that lag the upgrade and revising dynamic-link behavior by profile. At the same time, `AccessCell` tries to turn temporary access into a reusable runtime borrow state machine, while the reflection subsystem gains a nested metadata graph and generated registrations. The code review finds raw-pointer ownership hazards in safe clone/drop paths, a temporary commit with empty access operations, state synchronization that is not made safe by its “atomic” naming, unstable const/callable machinery, and duplicate old/new registration routes. These observations are source-level risks and broken checkpoints, not evidence that the final branch necessarily executed each defect. The month’s real contribution is to expose the cost of reimplementing Rust’s ownership and type-description machinery at runtime before capability semantics are fixed. Documentation corrections in the same period also show why this history distinguishes stated architecture from code that exists. See the [February 2026 review](loo-cast-vapor-semantic-diff-review.md#loo-cast-legacy--2026-02-bevy-018-migration-metadata-compiler-experiments-and-documentation-correction).

From January 2026, commit titles show renewed scripting work; February removes dynamic linking and restructures `core_mod_core`; March’s implementation makes one useful boundary concrete: Rhai composes descriptors, but the host executes only a finite catalog of Rust-registered signatures. In the same period, the USF prototype lets scripts register typed domain data—metrics, zones, density profiles and phenomena—while Rust owns sampling/classification operations and configuration chooses content. This points toward the owner’s later “Rust provides capabilities; Rhai composes behavior/content” formulation. But the implementation still relies on string-addressed schedule hooks, lifetime-erased Bevy access, per-kind file suffixes and local profile/modpack registries; it is not yet the later capability graph or Vapor pack model. Some source tests and manual visual reports exist, but the March semantic review remains marked in progress and does not establish the whole runtime as correct. See the [March 2026 review](loo-cast-vapor-semantic-diff-review.md#loo-cast-legacy--2026-03-rhai-bridge-becomes-a-catalog-driven-runtime-while-usf-prototype-restarts-in-parallel).

April is a documented authority reset: implementation is explicitly demoted to prototype evidence, a structured record separates owner direction from observed code, and the USF flow is reframed. A temporary matrix/vector facade follows, but core operations remain stubs. In May, process governance becomes explicit through phase gates, tracking issues, PR contracts and CI audit scope, while the Rust math experiment keeps changing shape and is still not an operational numeric foundation. June then makes knowledge provenance part of the collaboration model: raw answers, owner-confirmed claims and derived interpretations are distinguished, and the owner corrects earlier overreach around Vapor/USF/capability ownership. The glossary is summarized, annotated and its correction ledger rewritten more concisely; the May math tree and a sprawling diagram set are discarded. This marks a shift from reconstructing desired architecture from code to preserving the authority and uncertainty of design statements. The detailed [April](loo-cast-vapor-semantic-diff-review.md#loo-cast-legacy--2026-04-typed-usf-content-contracts-a-clean-slate-correction-and-the-start-of-process-rails), [May](loo-cast-vapor-semantic-diff-review.md#loo-cast-legacy--2026-05-phase-governance-an-expanding-knowledge-ontology-and-a-rustmath-restart), and [June](loo-cast-vapor-semantic-diff-review.md#loo-cast-legacy--2026-06-agent-bootstrap-question-led-architecture-correction-and-knowledge-base-consolidation) reviews track specific patches and remaining uncertainty.

That progression changes the epistemic status of the work. Before this period, intent is often reconstructed from code and commit messages after the fact. By spring 2026, the repository is deliberately preserving terminology, questions, decisions and “what is legacy” boundaries as first-class source material. This is not just documentation growth. It is a response to a project whose architecture is too broad and too easy to misremember when the code is being rewritten.

The question-batch protocol itself is an experiment in collaboration: one bounded set of questions, raw answers, then an “unlocks” summary, with implementation gated until the owner says to proceed. The owner’s stored answers in June/July repeatedly refine previous answers. So the logs should be read as a dated negotiation, not a frozen spec. For example: the initial desire for repo independence and crates.io publication coexists with the recognition that there is nothing substantive to publish yet; documentation first appears intentionally minimized, then the old glossary is recognized as foundational material worthy of selective migration; an initial four-repo split quickly prompts SDK/Launcher as separate repos, then shared-core consolidation later reverses that split.

### First Loo-Cast synthesis after the Rust/prototype era

The pre-Vapor sequence has not yet produced today’s full product architecture. It has accumulated several linked problems:

1. **Reusable core versus game-specific behavior:** the early Base Mod and Engine split, crate split, and later Engine/Game/Mod distinctions all approach this boundary from different directions.
2. **Authored extension versus unrestricted runtime code:** ScriptableObjects, commands, Lua, later capability/Rhai vocabulary, and eventually static Rust artifacts represent different attempts to let content express behavior within a host.
3. **Scale-aware simulation:** the space/universe problem becomes a deep engine concern and later USF; it does not automatically imply a finished universal scale framework.
4. **Reproducible assembly:** linker and build-script pain make it clear that “modularity” is incomplete if a user cannot reliably produce one runnable artifact from its parts.
5. **Architectural memory:** prototype resets and terminology churn create the need for glossaries, decision ledgers, source-corpus preservation, and question-based collaboration.

The strongest through-line is therefore not a single reused implementation. It is repeated discovery of the same boundaries under changing technologies: what can be authored, what is reusable, who owns runtime behavior, how extension identity and compatibility work, and how a complete game can be assembled without manually reconstructing the developer’s machine.

### Repo evidence and owner recollection must remain separate

The owner’s retrospective says this is a multi-year effort that began before Git. The Git history shows the work visible in the Legacy repo, then the long Unity→engine→Rust/prototype sequence. The 2026 first-person conversation establishes that the user wants the historian to reason about the human intent behind it, not just list repository metadata. That supports a careful interpretive narrative, but not invented biographical particulars. Whenever this document proposes a motive—such as wanting one authoring ecosystem that can represent the project’s own complexity—it is a hypothesis inferred from durable recurring choices, not a quotation from an unavailable 2021 conversation.

## The named Vapor phase: answers first, architecture second, repository objects third

### June 16–22: design pressure tests precede Vapor’s name

#### Capability and slot pressure-test (batch 003)

The June 16 capability batch needs to be read commit by commit. `27f97327` contains owner answers through question 60; `bc5d5400`, one commit later, fills 61–80. The batch itself says it is pressure-testing and correction, not doctrine production. This matters because the answers make a substantial model legible, but also preserve explicit uncertainty rather than resolving every term.

**Direction strongly stated in the answers:** the running `core_engine` should have one global capability graph, with package/game/mod views treated as projections. Raw declaration metadata might be a separate linear registry. The graph should be acyclic and assembled before its runtime lock; changes allowed by policy still happen during composition. A node is one capability, can link many other nodes, and may be composite. A slot is parent-owned and accepts one concrete capability type with a cardinality; filling it is a composition-time operation. `core_engine` plus its matching `core_mod` is one Engine fixture with two artifact parts; a playable product requires a Game, while a modpack selects an Engine, Game and their mods. Ordering should be automatic, and the proof before USF should exercise third-party composition rather than stop at a toy engine fixture.

**Execution boundary:** capabilities may be direct Rust bindings or composed branches. Rhai is itself a capability and may do simple local computation; the owner rejects a Rhai-only capability that has no Rust-backed host machinery and rejects using Rhai for heavy numeric work or orchestration. Capabilities emit intents; host `reconcile/commit/apply` performs canonical mutation outside the graph. Hook/event/message surfaces may be capabilities, but the owner’s broad “everything is capabilities” phrase is immediately qualified as “not literally everything” and “all depending on layer.” It signals a shared model, not a final universal node ontology.

**What remained open in the same source:** the owner could not choose whether dependency, slot, exposure and authority relations are one edge type or several; called authority vague; said the proposed slot-policy names were “mumbo-jumbo”; and left the minimum non-Spacetime bootstrap unspecified. Some answers were explicitly misunderstood or unanswered at first (`question 68` receives “What?”); the later answer file clarifies several Rhai/diagnostic questions but still says callback ownership is unclear. The capability/module AST unification, “capability type templates,” and all-assets-equal-capabilities proposal are therefore strong design hypotheses from a pressure-test, not implementation facts or a closed type system. The owner’s requested sequence was glossary revision, then a Phase 3 plan, potentially with more question batches; the same note asks to standardize that question-led collaboration method and trim `AGENT.md`. #### The 004a clarification: Steam is real, composition has multiple pack levels

The follow-up batch [`004a`](https://github.com/GHF-Studios/Loo-Cast-Legacy/commit/ca3968b06bd31031b58472737c525aee95838a40) tries to put a ceiling around the Phase 3 promise, but its answers make the target even more revealing. “Full public Vapor completeness” is accepted literally, while performance, polish, marketplace scale and public hardening may be deferred; the same answer set says nothing should be cut from the listed core proof. That is a real unresolved scope tension, not a clean acceptance boundary. Steam means all three of identity/authentication, Workshop acquisition/install and publishing; offline mode is still needed for authoring and local iteration. The Launcher is supposed to own a product-composition lifecycle distinct from Engine startup, construct the composition, diagnose invalid selections before launch, and show runtime logs after validation.

The proposed content structure also becomes more concrete: `enginepack`, `gamepack` and `modpack` are distinct author-facing composition units; `EngineMod`, `GameMod` and recursively nested `ExtensionMod` express where modifications attach. A mod has one parent in its inheritance tree, while capability dependencies may draw from the inherited ancestry. Nested modpacks remain organizational boundaries instead of being flattened away, and effective Engine/Game compatibility fingerprints extend as each composition layer adds or changes mods. `core_engine` and its matching `core_mod` are bundled as one Engine; `base_mod` is the Game and declares its Engine requirements. These answers foreshadow later pack semantics, but their names, relationship to the eventual fixed content-kind vocabulary, and meaning of “one running profile” were still being worked out (the owner floated `contentpack` and rejected unqualified `package`).

The proposed graph pipeline is staged: discover artifacts, form a user/modpack projection, perform shallow metadata prechecks, expand and validate the full capability graph, establish Runtime Lock, then enter runtime. The same file-per-leaf principle applies to Rhai assets and Rust kernels; ordinary content metadata should live in the authored file/folder declarations rather than Unity-style sidecar manifests. Yet the boundary between Rhai-side capability use and Rust-side kernels is explicitly called underexplored, the launcher/runtime graph handoff is answered “maybe,” and typed hook wording is deferred for another discussion. Follow-up answers also state that these are not empty proof fixtures: core extension points need multiple working example mods and several valid/invalid compositions. The batch supplies strong direction without closing the high-risk seams it was created to clarify. ### The scripting model becomes a layered runtime, not “a Rhai API”

The owner’s later design conversation extends beyond the first repo/Q&A batch and cannot be dated to a precise commit. It should be read as a working model the owner and assistant refined, not as a frozen accepted specification. A newly inspected Codex record gives an earlier dated contrast: the single-message “Hello World on Steroids” brief from 2026-08-30 explicitly says the old universal Capability Architecture is superseded, capability is only a USF runtime concern, and no Vapor-wide capability graph/custom compiler/strata should be built for the first vertical slice. It instead proposes ordinary Cargo/Rust composition of a minimal local Engine/Game/Mod example. The thread failed at the usage limit before any assistant answer or follow-up, so this is a dated owner proposal, not an accepted design artifact or implementation. The later Layer 1–3/Rhai meta-authoring direction in the current project context is a real subsequent reversal; the two should not be blended into one settled model. Its key correction is that **capability data and hook execution are separate mechanisms**: a hook is host-scheduled logic with identity, phase/schedule, cardinality and typed input/output; the contextual API graph is data passed into that invocation. A handle is a script-visible token for reacquiring a bounded host operation, not a Rust reference that survives its borrow window. Rust controls when the hook runs and constructs the handles; Rhai composes behavior through those objects. Any nested handle/capability structure should be shallow and broad enough to keep authority absent unless explicitly composed into a context.

The conversation then develops a layered code/runtime picture. These are owner-stated design semantics, not verified code:

| Layer | Intended ownership and lifecycle | Boundary still open in the discussion |
|---|---|---|
| 1 | Hard-coded in the engine’s Rust; each engine may define its own root machinery | What exactly belongs in the immutable root and how engines expose it |
| 2 | Rust additions compiled into the executable before launch; cannot be added after startup or unloaded at runtime | Composition/build contract and the exact boundary from Layer 1 |
| 3 | Runtime-extensible scripts/modules; Rust may be loaded/unloaded as constrained WASM | Sandboxing, ABI, validation, module cleanup and permitted host effects |

This attempts to reconcile an immutable authority root with powerful runtime scripting. Rhai is imagined both as a behavior-composition language and as a metaprogramming/authoring stage that can describe later API or capability graphs; Rust still owns compilation, linking, lifecycle and which context is available at each stage. The owner corrected the simple slogan “Rust provides capabilities; Rhai composes them”: the graph can recursively shape later authoring contexts, though the intended hierarchy stays shallow and wide.

Hooks and handles are also separate concepts. Rust chooses the hook’s phase/schedule, identity/cardinality and typed input/output, then provides a contextual graph of bounded handles. Scripts retain data between calls, not live authority: access closes with the invocation and a later call receives fresh handles. This resembles a syscall boundary, with hook-local remembered data as one possible context input. The Legacy January–March experiments are related evidence of the problem, but their unsafe lifetime-erased handles and hand-built registries do not implement or prove this model. The exact chronology of this design conversation is not pinned to a repository commit; these statements are owner direction, not implementation facts or a frozen spec.

### The intended content model emerges

The owner’s current explanation of the fixed content-kind vocabulary clarifies what those early manifests were for. This is authoritative owner direction as of this conversation, but code and older docs can still lag it:

| Kind | Owner’s intended role | Key distinction |
|---|---|---|
| `Packagepack` | Root of a complete playable selection; carries a runnable compiled executable and connects to source/edit/fork workflows | “Composition” is an informal synonym, not a second authored object or kind |
| `Enginepack`, `Gamepack`, `Modpack` | Typed bundle/manifests presenting grouped constituents, sometimes with mutually exclusive paths | A pack is not the container that physically owns the member source code |
| `Engine` / `Game` | Reusable engine machinery versus the game that uses it to express actual play/game-specific behavior | Engine defines what is possible; game defines what should happen in that game |
| `EngineMod` / `GameMod` | Reusable engine-level extension versus gameplay/content extension | Both are content kinds; their relations and dependency requirements must remain distinguishable |
| `ExtensionMod` | A mod of another mod, generically targeting a mod rather than one hard-coded subtype | Makes mod-on-mod ecosystems composable, while requiring explicit target and compatibility semantics |
| `Crate` | Vapor-managed ordinary Rust crate/library | Rust content can be statically linked; it is still content, but has a different authoring/build contract |

The pack/content distinction is crucial. Packs are typed manifests that define a selected assembly; content carries the actual reusable material and build inputs. A Packagepack is special because its deliverable includes a compiled, launchable executable, yet it also needs associated source and authoring workflows for editing/forking. The pack is therefore not simply a bag of files or a second name for a resolved runtime state.

There is a naming/model seam in the current Rust representation: the closed `ContentKind` enum includes all ten catalog entries, including the four packs, and source comments call each entry a “Content artifact.” The owner’s semantic language separates *Pack* (the authored assembly manifest) from *Content* (implementation/build material), while retaining one fixed catalog of ten types. That can be modeled cleanly as a closed set plus a pack/content classification; the current enum alone does not convey the distinction. This is not a request to add/remove kinds, but a warning against treating `ContentKind` as proof that Pack and Content are interchangeable domain categories.

The authoring backend does already branch on that distinction: its source scaffold returns `MetadataOnly` and does not add a Cargo workspace member for the four Pack kinds; Engine, Game, Mods and Crate receive code-bearing output scaffolds. The mismatch is therefore subtler than “the implementation treats them identically”: the generator knows Packs have no Rust crate, while the first IDE entry point still presents every kind under one “New Vapor content” form/action. The semantic information exists in one layer but is not yet reflected in the user’s choice of task.

The generic graph/composition split was also reached by correction, not fully present at the start. September 5’s first resolver is explicitly a Packagepack resolver that returns a validated composition. A later commit the same day factors recursive resolution into a generic `ResolvedContentGraph` and makes playable composition a Packagepack-specific validated projection. That is a useful early instance of the owner’s broader concern: a complete graph of Content and a runnable composition are related but not interchangeable. The October 24 draft revisits the same boundary with more explicit authoring/build/runtime/install projections; it should be read as a refinement of a long-running concern, not a brand-new idea that arose only in October.

There is also an observable mismatch between scaffolding and the stated static-composition target. In `scaffold_content_project`, Engine is a binary, Game and Mods are `rlib`+`cdylib` runtime libraries, Crate is `rlib`+`staticlib`, and Pack kinds are metadata-only. A separate `init_basic_content` helper creates an Engine package with both `src/lib.rs` and `src/main.rs`; Cargo will auto-discover a library and binary, but its Vapor manifest advertises only the binary. The same helper makes Game a library and Packagepack metadata-only. So Engine shape and declared artifact shape vary by authoring path. The intended model described by the owner is reusable compiled implementation libraries composed into an executable owned by Packagepack. Neither reviewed scaffold realizes that full build contract: the basic template has no Packagepack Cargo target, and the generic path makes Packagepack metadata-only. These may be provisional generators; the source does not document why the Engine shapes differ, so the causal explanation remains open rather than retroactively declared intentional.

The October 23 IDE offers a concrete example of why this distinction needs to shape workflow, not only documentation. Its first “New Vapor content” dialog iterates `ContentKind::ALL` and sends one `AuthoringAction::CreateContent` shape with an identity, version, required-dependency text and default Workshop metadata. The provider is kind-aware: Pack kinds are metadata-only, while implementation kinds receive Rust scaffolds. But at the UI contract, manifest-only Packs and implementation Content enter through one form. The owner’s model calls for Composer to compose existing content/packs into a Pack, while Developer authors the source behind Content. A single generic “create content” form risks collapsing those different operations again. It is a visible design seam to investigate, not evidence that the long-term model is invalid.

**Interpretation, high confidence:** Vapor is trying to own the semantic graph above both Steam and Cargo. Steam Workshop can distribute or expose provider items; it cannot alone define Vapor’s typed dependency, compatibility, composition or lifecycle semantics. Cargo can compile the Rust dependency graph; it cannot decide which game/engine/mod/pack a user selected or what those types mean. Vapor’s distinct graph should answer those questions, then drive provider and compiler operations.

That target is broader than “a mod manager for Loo-Cast.” It aims at a reusable ecosystem where engines, games, mods and packs are first-class, with a first-party Loo-Cast stack proving the model. Whether all ten kinds have complete validation, release artifacts, examples and UI is a separate implementation audit; current code is incomplete and contains mismatches documented in the evidence atlas.

### Static composition: the pivotal answer to Rust’s distribution friction

The rewrite bootstrap states its thesis plainly: old Vapor source was useful evidence, but not a trustworthy architectural authority. The first vertical slice was to start with Vapor-level declarations for a Terminal Engine, Hello World Game, Tiny Game Mod and Hello World Packagepack, resolve their semantic relations, produce the Cargo/Rust realization, statically link the libraries into a single executable, then launch it and prove each layer contributed behavior.

The key distinction is:

```text
Vapor graph: semantic intent, typed content, selection, compatibility
Cargo graph: Rust crates, compiler inputs, static libraries and executable
```

The first graph should derive the second. The reverse is not enough: a Cargo dependency list does not encode whether a dependency is a GameMod, an engine API, a selected optional path, or a Packagepack root. Conversely, Vapor cannot replace Cargo’s compiler and linker. The ambition is to use Rust’s static linking for dependable distributions while making compositions modular at authoring/build time. Content can be independently acquired and versioned, then assembled into one target-specific executable.

This addresses a central tension in modding: fully dynamic loading is flexible but imposes ABI, safety and deployment costs; bundling all code into one monolith makes independent authoring and selection impossible. Static composition is the chosen middle path for ordinary Rust content. It is not a sandbox: Rust build scripts and proc macros execute code during compilation, and pinned toolchains improve reproducibility without constraining capabilities. The owner’s later Layer 3 idea of dynamically loading Rust through WASM, and the related Rhai-generated Rust/metaprogramming escape hatch, are separate not-yet-complete paths—not properties automatically provided by static linking.

The rewrite’s own milestone report calls the initial slice “proven,” but carefully distinguishes that proof from what it did not prove: full Workshop publication, all pack kinds, rich dependency solving, mature distribution, or full authoring UX. That self-limitation is important. A minimal End-to-End proof is a foothold, not evidence that Vapor has already become the complete envisioned platform.

### July 17–20: delivery constraints force the content model into a real launcher

The 2026-07 commits across Client, Installer, Examples and Loo-Cast make a shift from source-centric development to player delivery. The content workspace declares target-aware runtime payloads and a Windows GNU-LLVM target. - A **developer** has source repositories and builds with the pinned Rust toolchain.
- A **composer** chooses existing content and produces a new Packagepack; the later owner clarification permits Cargo manifest composition but not authoring Rust source as the ordinary Composer role.
- A **player** should acquire a target-ready executable and content through the launcher without Git, Rust or a local build step.

July 20’s “player bootstrap away from Git” is especially consequential. It closes a dangerous conceptual shortcut where “source checkout available to the developer” had been mistaken for “player can launch the artifact.” The platform must publish/serve build outputs separately enough that a non-developer Windows laptop can install and run a composition. The repeated Windows launch fixes then become evidence that a one-OS developer workflow was not sufficient.

The Installer starts July 18 as a separate lifecycle/bootstrap tool. The simple player/developer split later proved insufficient once Composer was defined as Cargo-backed but Rust-source-free.

The Installer later adopts the shared Client operation API and GUI host, while retaining a standalone recovery executable. This reflects a bootstrapping paradox: the setup product needs an executable before managed tools exist, but ordinary lifecycle semantics should still be owned by the same service as CLI and GUI. Standalone recovery packaging and shared domain/API ownership are compatible; the former should not become a second implementation of install semantics.

### October: user workflows, service model, and IDE meet—without converging completely

October history makes the product stack concrete. `Vapor-GUI` hosts product UI; Studio and Installer are integrated as GUI modes; player Launcher gets separated into a simpler workflow; IDE surfaces workspace files, editor and diagnostics. CLI and GUI consume the shared Client service. Installer handles role promotion, bootstrap and installation. Steam entrypoint selects an app mode or directly launches the selected composition. Vapor Studio grows Workshop discovery/subscriptions, Library, package/composition authoring, source projects, publishing and operations views.

The entrypoint diff history records how that route was reached: first a terminal wrapper forwarding everything to `vapor-launch`; then direct GUI/product dispatch; then a correction to no-argument direct composition launch plus explicit `chooser`. The owner independently confirmed the two intended launch options and both target paths. This makes Steam’s simple pair part of the product model, not an arbitrary collection of unrelated app launch flags.

The owner later made the first-launch contract explicit: require setup before play and choose the installation role in that same setup. `Vapor-Installer/2592142` implements the visible flow, but the latest state does not enforce one unified completion predicate: Installer combines an app-root Player receipt with user-data role/readiness state, while direct Steam Play checks only the Player receipt. As a result, the UX says “selected role setup required” while Steam's launch authority effectively says “Player files initialized.” The current audit also finds that Player setup itself initializes the canonical developer Superworkspace and machine-level Vapor PATH integration. This boundary must be judged against both explicit owner intent and player simplicity; neither consequence should be mistaken for an owner-authored requirement merely because the current setup path performs it. See the [current-state role/setup analysis](loo-cast-vapor-semantic-diff-review.md#october-25--installer-role-and-setup-state-do-not-share-one-authority).

The October 25 source trace sharpens the bootstrap paradox: a precompiled Installer is justified because first-run must work before Rust/Cargo, but the current product uses the shared Client service only for role transitions. Status, install, repair and uninstall still run locally through Core, while first-run tool setup compiles a second copy of the shared app-root helper into Installer. The role operation has service progress machinery, but Installer renders only final status; its direct lifecycle jobs also bypass service operation reservations. This is a boundary consequence, not an argument against a standalone bootstrap executable: the executable can be exceptional while the lifecycle semantics remain single-owner. The same distinction appears in teardown: Core has explicit external-user-data/Superworkspace purge flags, yet Installer does not expose them; September's source-preservation checks are network-mutating and sequential rather than atomic rollback. See the [Installer ownership and teardown trace](loo-cast-vapor-semantic-diff-review.md#october-25--installer-is-a-partial-service-facade-with-a-second-bootstrap-owner).

The IDE’s vocabulary evolves beyond “text editor.” It starts as service-backed workspace/file editing; selected October 23 patches add typed Rust/TOML/XML/Rhai projections, a bounded semantic index for objects inside files, structured diagnostics, canonical Rust item/module creation and version-aware LSP request tracking. This matches the owner’s boldest IDE intention: Vapor should understand the artifact model and Rust module organization, let files and semantic objects be addressable, and provide a performant editor/console across the game and tools. The real code is a partial foundation: there is no complete canonical semantic object model for every file type or universal custom inspector system. The current service does launch Rust Analyzer against the selected source workspace’s pinned toolchain, but the analyzer must already be installed; source does not establish automatic provisioning or one shared analyzer process across frontends. Nor do the reviewed paths show all editor operations honoring one unified authoring contract. See the [IDE and LSP review](loo-cast-vapor-semantic-diff-review.md#october-23--lsp-edits-gain-explicit-safety-rails-the-ide-grows-into-a-separate-subsystem).

The shared service and operation model grew to include status/progress, sources, console records, Workshop operations, toolchain management, publishing and logs tagged by origin. But the existing evidence atlas records protocol/service mismatches and user-reported failures: operations advertise queueability while backend may reject resource conflicts, refresh can appear hung, Windows startup/role promotion is fragile, and visual/console behavior remains uneven. The history’s increasing abstraction is therefore both real progress and a warning: API shape can get ahead of behavior. User’s later requests to see operation progress and to keep output attributable to Launcher/Studio/IDE/game directly respond to that observability gap.

The service chronology is more nuanced than a smooth extraction from UI: Studio first accumulated its own typed child-process protocol, fixture simulator and service-owned operations. Workspace discovery, profile state, file access, authoring, and Workshop work crossed that boundary in stages. Then the Studio-specific service/client/protocol crates were deleted, and the design itself was marked superseded as Studio joined the shared Client service. That is strong evidence of an explicit ownership correction toward one domain service for multiple frontends. It is not proof that every operation has completed the migration, nor that process startup, shutdown, persistence and cross-platform behavior are all correct; those need current source and runtime evidence.

The user’s recurring Player → Composer → Developer → first-party ecosystem developer layering supplies the product’s information architecture. These are cumulative capability sets, not unrelated app modes: the Player should see Play/Discover/Install; a Composer unlocks composition from content and may need Rust/Cargo tooling to link it, but does not write Rust; a Developer authors source and uses IDE/toolchain; first-party ecosystem work adds registry/server/publishing/operational authority. Installation role, UI workflow classification and remote authorization are different axes, even though the experience must explain them coherently.

#### October 15–25: lifecycle semantics meet the boundaries they have to cross

The mid-October code begins turning the Workshop into a lifecycle rather than a search page: Steam owns discovery and account subscription facts; Vapor acquires a separate cached Library copy; installed Packagepacks retain a resolved playable graph; Auto-Install owners control required dependencies; and a persistent selection drives launch. This is not just extra state. Each transition crosses a different authority—Steam callbacks, local cache/index, persisted composition state, installed files and process launch—so there is no single transaction that can make the whole sequence atomic. The source review finds the seams where that matters: a partially successful subscription batch can leave the UI snapshot stale; cache activation and composition persistence can diverge; Auto-Install ownership can lose exact versions; and the real-service enable path can accept an action that the application layer later rejects. These are implementation defects at the joins, not evidence that the intended lifecycle distinctions are wrong. See the [Workshop and Library trace](loo-cast-vapor-semantic-diff-review.md#october-15-19-steam-discovery-grows-into-a-separate-subscription-and-library-lifecycle) and [current Auto-Install review](loo-cast-vapor-semantic-diff-review.md#october-25--enabling-auto-install-has-no-successful-real-service-path).

The IDE follows a parallel trajectory. It starts from files and adds selectable syntax projections, a semantic index, a Rust Analyzer connection, diagnostics and typed module creation. That begins to make source artifacts navigable through Vapor concepts, but it does not make the projections one semantic authority: Rust Analyzer, local Rust/TOML/XML/Rhai adapters, Cargo diagnostics and Vapor manifests still know different things. The distinction mirrors the rest of the product: common envelopes and UI affordances are useful, but shared shape alone does not mean shared semantics. The Oct 23 workbench is therefore a real step toward the July screenshot’s integrated authoring environment, while remaining a partial and uneven implementation of it.

The October operating model also exposes a central tension in the vision: one local service should make Launcher, Studio, IDE and CLI facades over the same operations, but IDE workspaces and operation contexts can still be frontend-local while the service holds one global workspace root. The implementation is moving toward one authority without yet transporting enough identity to preserve independent contexts. Likewise, the accepted Registry role places Vapor semantics above Steam, but current Registry code still models repositories and ecosystems rather than the Workshop catalog. These two examples distinguish an architectural destination from current ownership: the user is trying to make Vapor the integrator of content meaning and lifecycle, while current code often only connects the tools and providers that already exist.

This causal reading is supported by the owner’s repeated corrections and by the October source paths; it is not a claim that every user motivation can be recovered from commits. The detailed current-tree defects and their confidence boundaries live in the [evidence atlas](vapor-ecosystem-evidence-atlas.md) and [semantic review](loo-cast-vapor-semantic-diff-review.md).

## What the human appears to be trying to build

This is the central interpretation, supported by repeated explicit owner statements rather than by repo names alone. It should remain open to correction.

### The likely aim

The owner seems to be pursuing a **creator-owned software/game ecosystem**: a player can install and launch a complete playable selection; that same selection is a first-class Packagepack that can be inspected, modified or forked; a composer can combine already-published content into another pack; a developer can author actual Rust/Rhai content; and first-party ecosystem developers can modify the platform, registry and services. The whole path should share one typed vocabulary, one authoritative service and one connected workspace model, so users do not have to know the hidden technical plumbing before accomplishing their task.

The ambition is not merely “make a nicer launcher for Loo-Cast.” The launcher is supposed to make a multi-content ecosystem feel accessible. Studio should compose and publish packs. The IDE should make the Rust/Rhai/configuration objects behind content understandable and editable. Installer should make capability/role transitions explicit. Steam should provide reliable distribution/launch anchors, while Vapor supplies meaning Steam lacks. Examples and the terminal wheel game are not side curiosities; they are deliberately different compositions used to prove that the ecosystem is not hard-coded to Loo-Cast.

### Why the user cares about seemingly small boundaries

The user repeatedly objects to names and panels that duplicate or misrepresent a concept (“Composition” versus Packagepack, “Library” as crate kind versus installed-content Library, current-folder assumptions, raw cache state in a player UI, three app modes presented as “GUI,” etc.). This is not cosmetic pedantry. The apparent belief is that **a UI inconsistency is often evidence of a missing or split semantic owner underneath it**. If Workshop subscriptions, local Library, installed content and composition membership disagree, changing labels alone is a superficial fix; the lifecycle model must be unified. If the IDE shows Rust files as generic folders, file navigation may not understand Rust’s semantic modules. If Windows asks for a `Workspace.vapor.toml` that cannot exist in a Steam depot, discovery is based on the wrong root contract.

The project’s “dogma” request is consequently about making invariants visible and enforceable—not about enforcing arbitrary style rules. The user wants Vapor to own a coherent model deeply enough that ordinary operations are safe and discoverable, while still allowing authors to escape into lower-level Rust where necessary.

### Human–assistant collaboration is part of the project history

The Q&A logs and current conversation indicate a distinctive collaboration model. The user thinks by injecting context and revising a prompt while the design is in progress; a seemingly small aside can alter product boundaries. The assistant’s job is to hold the implementation and historical detail, but the owner remains semantic authority. Early logs strictly required questions and approval before edits; later the owner deliberately authorized large autonomous passes, real builds and Steam publishing. Neither instruction set is timeless: they record different task periods and must be interpreted by date and immediate authorization.

An educated guess is that the user is trying to use the assistant as a very fast second engineering mind while retaining human intuition for product meaning. That explains insistence on recording raw answers and not flattening uncertainty into doctrine. It also explains frustration when an agent rapidly implements something “technically checked off” but misses a product boundary that was implicit in the larger context.

This reconstruction combines owner recollection, dated design answers, repository chronology, and selected source-pinned diffs. Its central historical interpretation remains provisional where the pre-Git 2021 record is missing. Recent exact-source checks corrected two easy-to-misread areas: the July 2024 event-to-request rename did not itself add stored request payloads, and August `save_entity` / `save_chunk_actor` methods only removed live references from in-memory registries rather than preserving serialized state. The adjacent chunk scene serializer is a separate in-memory path, not proof of durable disk persistence. These distinctions are recorded at the relevant dates in the review ledger.

The current pass deepened the August–September 2023 save/chunk lineage from commit summaries into exact diffs and files. The Sept 2 `7e445030` generator runs callbacks while holding both bookkeeping mutexes, silently discards a duplicate-position callback, and has no worker shutdown/join path. The Sept 5 `e452f605` revision adds shared-state bookkeeping and guards but leaves the sequential blocking-receiver topology; three spawn branches route to the load sender. Its successor `37495a30` removes channels but replaces them with an unpaced outer loop that repeatedly logs while idle, while the Universe observer's state arms are empty and the plugin does not register its spawn/despawn wrappers. The worker only advances states/callbacks; it never calls generation/load/unload, and the same tree's spawn path unwraps a chunk-map lookup with no scheduled path that populates it. These are source-level findings, not claims that the revisions were run. This strengthens the pattern from “an async attempt remained incomplete” to “the main owner path and the operation executor were both disconnected in the inspected snapshot.”

The November 2023 exact-diff pass shows that the later staged state model does not settle the contract. `81f48474` adds separate Registered/MetadataLoaded/DataLoaded enums for chunks, clusters and entities around placeholder payloads and nested `Arc` locks. `1d609519` empties three cluster methods that still promise values; `6c20d5ba` replaces panics with `Result` but its new `Vec::append` assignment yields unit and several branches return bare values where a `Result` is required. The subsequent source split (`4df99666`) contains field/constructor type mismatches. Position-aware demand arrives in `1e960e02`; then `a91b890d` adds an ECS entity to the run state while commenting out the public transition methods. `2ebcd38d` switches children from global IDs to local-position keys but leaves global position calculation as a TODO and comments out the operations. This repeated sequence is stronger evidence of a moving ownership model than of one steadily integrated streaming design. Exact details and evidence limits are in the [November hunk supplement](loo-cast-vapor-semantic-diff-review.md#hunk-level-supplement-november-2023--identity-ownership-and-api-churn). No historical revision in this pass was built.

The December 2023 GlobalUniverse pass makes a more meaningful ownership move—operation helpers accept borrowed chunk state rather than resolving identities internally—but the API is still internally at odds. The root map changes to direct `HashMap<LocalChunkID, ...>` ownership while lookup retains `.lock()` and the old position key; the new one-shot callbacks do not match the dispatcher calls; root variants have no dispatch arms; and the spawn helper only flips a state enum while its Bevy command parameter is unused. This is an important distinction: the design is trying to put identity lookup and mutation at one explicit boundary, but the actual snapshot does not close that boundary.

The January 2024 Cargo split moves from directory language to package boundaries, but its first BaseMod package is still Cargo-template `add` code. The workspace manifest later uses a case-mismatched member path on Linux, while the immediate compile-cleanup comments out player and observer chunk operations and leaves their view bookkeeping active. The accompanying PowerShell builds also expose operational ownership gaps: nested current-directory changes make the first script's paths point to siblings incorrectly; a later script renames every important path variable but leaves build/cleanup/copy/launch referencing undefined old names. These examples connect the later Vapor demand for a single owned build workflow to a real historical need, rather than treating it as a new preference without precedent.

The same month’s manager and native-mod experiments show why “a dependency graph” or “dynamic modules” is not enough as an architecture. The custom manager code repeats lifecycle state and `TypeId` maps across domains; its worker holds the root mutex, adds child→root edges, and then calls child initialization. Each child initialization locks its root dependency, so the source contains a direct non-reentrant mutex self-deadlock path. Startup has no barrier that waits for this worker, and finalization cannot acquire the root mutex it retains. The mod loader declares identity and dependency methods but does not use them to order modules; its helper searches for `mod.dll` while the caller constructs a path from the directory name instead. More seriously, `register_mod` installs Bevy systems from the module, but the loader’s local `Library` drops as registration returns; scheduled function pointers then outlive their code owner. The exported `dyn Mod` pointer also has no stable cross-compiler C ABI, and its raw allocation is not reclaimed in the host path. A separate Lua hello-world thread has no observable completion/error path and changes Engine’s crate type to `rlib` while the mod remains a dependent `cdylib`, leaving duplicate Engine globals possible. These are source-level risks, not reproduced failures. They anticipate questions later made central to Vapor: who owns dependency resolution, who owns executable code lifetime, and what host-controlled contract crosses a content boundary? See the [January 2024 manager/mod-loader review](loo-cast-vapor-semantic-diff-review.md#hunk-level-supplement-january-2024--manager-graph-and-native-module-lifetime).

February’s source review adds a useful correction to the “commands replace direct access” narrative. Player and LocalUniverse temporarily disable the old operations, restore them while the new command layer remains skeletal, then comment out Player’s spawn path again as command resources are injected. The processor signature, its registered call and the body’s references to old state diverge in the same checkpoint; Player startup also loses the visible local-universe registration. By Feb 20, `InfoHierarchy` has been extracted and implemented, but GlobalUniverse still mutates it directly. Parent and child metadata records use strong `Arc`s in both directions, and removing a root does not recursively detach descendants; this is a source-level cycle/lifetime risk, not evidence of a measured leak. The sequence matters because it separates the valid architectural desire—centralize identity and operations—from the actual implementation, where several owners coexist and the consumer migration is unfinished. See the [February 17–20 hunk supplement](loo-cast-vapor-semantic-diff-review.md#hunk-level-supplement-february-1720--command-ownership-remains-transitional).
