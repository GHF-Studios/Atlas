# Console and Editor Design Crosswalk

**Observed:** 2026-10-26. This compares the shared console/editor design, the later Vapor command-console design and plan, and the current game/Vapor source. It checks implementation boundaries, not rendered UI or live stream parity; no GUI, terminal session, build or test was run for this crosswalk.

## Design lineage

The October 22 [shared console/editor design](</home/leslieghf/Vapor/Vapor-Client/docs/superpowers/specs/2026-10-22-shared-console-editor-core-design.md>) separates host-neutral meaning from host-specific commands and widgets. Its core owns structured records, style roles, bounded history/filter behavior and shared Rhai lexical rules, while avoiding Bevy, egui, service access, file I/O and persistence. Game, Vapor GUI and CLI keep their own command authority and rendering adapters. The document records an implemented semantic slice and explicitly denies full visual or console parity.

The follow-on [Vapor command-console design](</home/leslieghf/Vapor/Vapor-Client/docs/superpowers/specs/2026-10-22-vapor-command-console-design.md>) adds a narrow typed Vapor command surface and one structured operation-output stream. The [implementation plan](</home/leslieghf/Vapor/Vapor-Client/docs/superpowers/plans/2026-10-22-vapor-command-console.md>) calls for descriptors shared with terminal help/completion, typed service dispatch, managed process labels, progress normalization, a resizable Studio console, read-only Launcher console, and shared IDE operation output. History: `6df6854` adds the shared-core design, `a168973` records its implementation slice, and `bcde79b` adds the Launcher lifecycle/console pass. These design artifacts are useful dated snapshots; their acceptance lists are not runtime proof.

## What is shared now

- `vapor_console_core` is host-neutral and owns structured `ConsoleRecord` data, severity/style roles, filtering, bounded history/prompt history, command-line tokenization and Rhai token categories. It has no process or UI dependency. [Shared model and record types](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_console_core/src/lib.rs#L1-L180>); [Rhai rules](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_console_core/src/lib.rs#L447-L505>).
- The Client protocol carries operation ID, origin, composition, stream, timestamp, level, source, action, optional process label, diagnostics and original machine-readable output. A bounded event queue preserves an omission notice when output is dropped. This is structured transport, not proof that every tool emits complete process metadata. [Protocol output event](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_protocol/src/state.rs#L539-L580>); [bounded service output queue](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_service/src/session.rs#L90-L149>).
- `vapor_gui_core` provides one filterable console presentation model for Launcher, Studio and IDE. The CLI adapts records to terminal styles. The game converts its local command/tracing records to the shared semantic record and the workbench uses the shared Rhai language rules; it retains its own console window, Bevy command registry and lifecycle. The shared layer therefore standardizes semantics and some GUI-to-GUI presentation, not a cross-product widget.
- Vapor command descriptors and parsing currently live in `vapor_client_domain::console_command`, where they can produce typed `ClientAction`s without making the host-neutral console core depend on the Client domain. This is a sensible dependency-direction refinement from the first design's loose placement language. The catalog is deliberately small: help, status, catalog refresh, composition selection/launch and a few workspace tools. The broad CLI grammar remains Reedline/CLI-owned; “one console” does not mean one universal command language.

## Remaining gaps against the plan

The shared-editor design is strongest at record/token semantics; it does not share buffer/file semantics, visual widgets, Rust language analysis or editor document lifecycle. The language sharing covers Rhai lexical categories, not a unified Rust/Rhai semantic-object system or identical rendering. Different egui versions remain separate, as intended.

The command console has a typed path, but descriptor reuse in terminal help/completion remains open. Severity and process identity are structured where supplied, yet the source does not establish that every child process is named, that ANSI progress is uniformly normalized, or that all setup/toolchain output is live and lossless. Operation records can be bounded/dropped with an omission indicator; they are not a durable full log archive. The design correctly treats the game registry and Vapor service actions as disjoint capabilities.

The visual requirement is also not settled by these artifacts: the in-game F2 console is a reference for hierarchy and interaction, while the GUI uses a different host/toolkit adapter. The source confirms panels and filtering exist, but only a human runtime pass can establish whether height is draggable, scrolling is responsive, typography matches, or the full output remains readable under load. No such check was performed here.

**Disposition:** shared semantic records and Rhai token rules are implemented; command invocation is partly unified through typed Client actions; command grammar, UI widgets, game command dispatch and editor document lifecycles remain intentionally host-specific. “Clone the F2 console” means reuse its useful interaction principles and shared semantics, not merge its ECS command system into Vapor or claim exact UI parity. The plan's remaining process-stream, terminal help and live parity gates remain open.
