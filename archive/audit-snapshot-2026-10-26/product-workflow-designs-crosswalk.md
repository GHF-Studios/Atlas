# Product Workflow Designs Crosswalk

**Scope:** three uncited workflow designs that shape the Launcher/Studio/Client-service boundary. This records what each document said, how it relates to later owner direction, and what the inspected latest source actually does. It is not approval to revive superseded designs.

**Evidence limits:** the three design documents were read in full. Current implementation evidence below is cross-referenced to the latest-state audit, which inspected the named source paths. Git history was checked for the source documents and for the service-design handoff. No runtime, Steam account, or deployed service was exercised for this crosswalk.

## 1. Studio service-boundary design (October 17–18)

The October 17 design proposes a short-lived child service owned by a Studio GUI session, with stdio JSON-RPC, one interactive client, GUI-owned startup/shutdown, a terminal simulator, semantic actions, service snapshots, deterministic providers, and scenario traces. It correctly identifies that direct calls to `vapor_studio_core` did not exercise the GUI's worker-thread orchestration and result handling. Its opening status banner explicitly marks that process model superseded by the shared Vapor Client Service.

The implementation history confirms the pivot: Vapor-Studio commits `816ba40` (October 17, service-boundary foundation) and `ef6e6b1` (October 18, move Studio onto the shared Vapor Client service) bracket the change. The first document's implementation-status block is a dated snapshot, not current status. The durable parts are the distinction between workflow authority and presentation, typed semantic actions, operation observability, and GUI-independent scenarioability. The obsolete parts are the Studio-specific service executable/session, one-client limit, GUI-owned lifecycle and any expectation that Studio gets a separate workflow authority.

The present source cross-reference finds a shared service session used by multiple frontends, serial request dispatch with background work returning as typed completions, and a common durable state. It also finds incomplete operation families and some Studio UI-side state/worker handling. Therefore the architectural move is real but the aspiration “frontends only present and request typed operations” is not complete. The old design's service-testing ideas remain useful, but need to target the shared service rather than a Studio-local child. See the [shared service session and operation path](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_service/src/session.rs#L162-L249>), [service dispatcher](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_service/src/session.rs#L1644-L1745>), [Studio shared-service integration history](https://github.com/GHF-Studios/Vapor-Studio/commit/ef6e6b1), and the [current service-boundary review](current-state-semantic-cross-reference.md#the-shared-service-has-one-serialized-owner-but-not-yet-one-operation-contract).

**Disposition:** service-boundary objective remains valid; Studio-owned process and protocol design is superseded. Current code has the shared-session core, not full GUI/workflow decoupling or scenario coverage.

## 2. Studio content-lifecycle design (October 18)

This design anticipated much of the player-facing lifecycle: distinct Play/Compositions, Library and Browse destinations; acquired content appearing in Library; packages remaining playable selections; source authoring kept separate from selected playable state; one canonical `~/Vapor` Superworkspace; exact ten-kind vocabulary; and one shared Client service behind Studio, CLI, Installer and Steam paths. It also warns against exposing receipts, cache paths, and provider mechanics to players. Those are strong product and ownership boundaries.

Several decisions were later refined or directly superseded:

- **Composition identity:** the design makes Composition a separately durable object backed by Packagepack. Later owner direction says “composition” is an informal synonym for a playable Packagepack, not a second product identity. The checked-in domain still stores a distinct `Composition` and active selection; the mismatch is present in both design and implementation, not just a stale label.
- **Persistence migration:** the design prescribes a schema 1→2 migration preserving profiles and installed compositions. Later direction for the current alpha explicitly permits regenerating fresh local state and removing local userdata rather than doing this migration. Treat the migration as a dated design choice, not an active requirement.
- **Composer/Developer boundary:** the design correctly keeps source authoring separate from playable selection, but its Crate wording can be read as making Composer Rust-free. Later owner clarification: Composer may use Rust/Cargo compositionally (including Cargo manifests) but does not author Rust source; code authoring/build implementation belongs to Developer.
- **Auto-Install/subscription:** the design says subscription, cache removal, and composition membership are independent, and that Auto-Install is not Subscribe. Later owner direction gives Auto-Install an ownership policy: it can control automatic version updates and removal/unsubscription when no composition needs a constituent; disabling it for an already-used constituent can imply a user-owned manual subscription. The old independent-state rule is therefore incomplete. Explicit user unsubscribe versus removing an auto-managed dependency still needs a precise operation contract.

The current service has a persistent active composition selection and a default-seeded Packagepack path; it does not implement the later one-identity Packagepack contract. The current authoring flow exposes all ten kinds under one `CreateContent` operation. Pack templates are metadata-only and avoid Cargo workspace membership, but the service action still classifies all such creation as Developer; there is no distinct Composer operation combining acquired compiled content into a Pack. Workspace authoring state is separate from the selected playable state, matching one important invariant. Current code therefore implements selected slices, while identity, role semantics and the actual composition operation remain misaligned. See the [active selection and default seed](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_service/src/session.rs#L549-L619>), [default Composition record](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_domain/src/composition.rs#L323-L349>), [content creation action classification](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_domain/src/actions.rs#L448-L467>), [metadata-only Pack templates](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content/authoring.rs#L405-L450>), and [current Composer/Developer cross-reference](current-state-semantic-cross-reference.md#content-authoring-operations-cross-the-playercomposerdeveloper-boundary-differently-from-pack-payloads).

**Disposition:** retain the separation of authoring context from play selection, the ten-kind vocabulary, one shared service, progressive disclosure and local/remote state distinctions as evidence-backed product direction. Do not carry forward a second Composition identity, mandatory migration, or the old narrow Auto-Install semantics as settled policy.

## 3. Launcher content-coherence design (October 22)

This parent-repository design is a focused implementation plan for reported defects, not a complete ecosystem content contract. Its Git history begins with commit `bcde79b` (October 22), “Document launcher lifecycle and shared console pass.” Its strongest principles remain: one persistent player selection; one item identity through Workshop, subscription and local availability; typed filters; bounded paging; one primary action; contextual disclosure; and a service-owned state machine. It correctly distinguishes Steam's remote page size from local row paging and says Workshop tags are additional labels, not the authority for canonical compatibility.

Current implementation covers parts of the plan. The Launcher has a persistent selection, distinct Discovery and Subscriptions projections, paging, row selection and local content-kind display/filtering. The inspected search path requests a typed kind; the subscription view filters locally. Canonical kind is inferred from local manifest where available and otherwise from Steam tags, so untagged/incorrect legacy items can disagree across views. The subscription panel has no equivalent list virtualization/paging guarantee in the inspected implementation, and the typed-filter behavior has remaining edge cases. The default alias is still seeded in state. See the [selection and default-seed cross-check](current-state-semantic-cross-reference.md#launcher-a-player-facing-projection-with-partial-shared-service-semantics), [Workshop filter and paging cross-check](current-state-semantic-cross-reference.md#workshop-type-filtering-is-a-steam-tag-contract-while-acquisition-crosses-several-authorities), [Launcher composition surface](</home/leslieghf/Vapor/Vapor-Client/Vapor-GUI/crates/vapor_launcher_ui/src/lib.rs#L570-L689>), and [subscription projection](</home/leslieghf/Vapor/Vapor-Client/Vapor-GUI/crates/vapor_launcher_ui/src/lib.rs#L1287-L1464>).

The plan's requirement that `Unsubscribe` never remove local content, and its separation of Auto-Install from subscription, predate the later owner clarification that auto-managed Packagepack constituents should be removed/unsubscribed when no longer required, while manual acquisition should remain user-owned. Those are not safely reconciled by treating every unsubscribe as a destructive cascade: explicit unsubscribe, Packagepack uninstall, Auto-Install ownership, shared dependencies, and manual retention are distinct intents that need a typed transition model. This is a real open semantics seam, not a wording-only issue.

The design originally excludes real Steam publication. That was a scope limit for this particular UI pass; later user authorization explicitly allowed public Workshop publication for testing. The statement is not a permanent product-level prohibition. The document's requested local deploy/verification gate also does not prove that the subsequent public items are correctly typed or that every platform can install them.

**Disposition:** substantial implementation target and useful UI requirements, partially realized in current Launcher. Its one-selection and typed-filter intent remain; Auto-Install ownership and the permanent reading of “never publish” are superseded. The source document's implementation status does not itself certify acceptance.

## 4. Repository-boundary migration and product-surface revisions (October 14–20)

The October 14 repository design makes an unusually concrete ownership claim: Vapor owns reusable domain and operation machinery; Vapor-CLI owns command grammar and terminal presentation; Vapor-GUI owns a reusable GUI host/core; Studio and Installer are product modules hosted by that GUI; the Steam entrypoint dispatches. The accompanying implementation plan breaks that migration into source-to-destination inventory, shared capability moves, a single CLI, GUI host, Studio and Installer modules, entrypoint routing, and repository lifecycle. It is explicit that its “two frontends” are CLI and GUI, and that one Studio product includes library, composition, workspace authoring, publishing review, diagnostics, and play selection.

The parent repository history records the main migration landing in `41c62e6` on October 14: submodule gitlinks for old Launcher, SDK, Shell and Entrypoint paths were replaced by Vapor-Studio, Vapor-GUI, Vapor-CLI and Vapor-Steam-Entrypoint; the same commit updated `.gitmodules` and the repository-boundary design. This is strong evidence that the local superworkspace structure changed as planned. The current `.gitmodules` continues to name the new repositories. The supplied conversation also records that GitHub repository rename/create/archive operations and pushes completed, but this crosswalk did not independently query GitHub or verify present remote metadata.

The design's product boundary was then revised, not simply implemented as originally written. The October 20 owner-approved decision splits the graphical audience surfaces into Launcher (player), Studio (creator), and IDE (code author), with CLI as a fourth facade; all share the Vapor Client service and canonical model. The change is documented by `7825e12` and is explicitly incorporated near the top of the October 15 lifecycle design. Thus “two frontends” in the October 14 plan is a dated migration boundary, not the current product model. Repository decomposition and product decomposition are separate axes: three audience-specific experiences currently live as UI crates assembled by the Vapor-GUI executable, while the Steam entrypoint dispatches chooser, play/launcher, Studio, IDE, Installer and shell modes. A distinct experience does not necessarily imply a distinct repository or process.

Current checked-in structure supports some, but not all, of the later decision. The parent `.gitmodules` points to the renamed shared/product repositories; `Vapor-GUI` has separate Launcher, Studio and IDE UI crates and a chooser; its executable maps modes to product apps. The Steam entrypoint recognizes those product modes. This demonstrates product routing and module separation, but not the full service-only facade contract: the same executable assembles all GUI products, and current UI code still has workflow-specific state/worker paths documented in the current-state review. The October 20 design itself correctly warns that product separation is not evidence of separate binaries or complete service isolation. See [the parent submodule map](</home/leslieghf/Vapor/Vapor-Client/.gitmodules#L1-L24>), [GUI mode and product assembly](</home/leslieghf/Vapor/Vapor-Client/Vapor-GUI/crates/vapor_gui/src/lib.rs#L44-L57>), [chooser product entries](</home/leslieghf/Vapor/Vapor-Client/Vapor-GUI/crates/vapor_gui/src/lib.rs#L165-L206>), and [Steam entrypoint mode labels](</home/leslieghf/Vapor/Vapor-Client/Vapor-Steam-Entrypoint/crates/vapor_entrypoint/src/main.rs#L428-L440>).

The repository plan also freezes the Steam launch-option contract during its migration and says not to deploy or publish. Those were constraints for that migration tranche. Later, the owner explicitly changed the launch-option target set to one direct Loo-Cast launch plus one chooser, with platform-specific variants, and separately authorized Steam testing/publication. The earlier plan must not be used to deny those later decisions. Conversely, user authorization to publish for testing does not make publication an ordinary player workflow or prove a particular upload correct.

The migration plan's release notes say repositories were renamed only after local source and parent-reference changes were reviewable, and the parent commit records those local gitlink changes. But it is not sufficient evidence that all remote repositories, release jobs, app depots, Steam entrypoints, and downstream clones now agree. The migration's core source topology is current evidence; remote administrative state and cross-platform delivery require their own records and verification.

**Disposition:** the October 14 structural migration is substantially present in the local checkout and parent history. Its bundled Studio/Installer frontend model and two-frontend product taxonomy were later revised. Preserve its one-shared-implementation and acyclic dependency-direction goals as architectural intent, while checking current service contracts and packaged executable boundaries independently. The October 14 plan and October 15 lifecycle plan are executable plans with dated completion notes, not proof every checkbox remains current or every later owner decision has landed.

## 5. The October 15 lifecycle plan and October 20 product decision

The lifecycle plan is broader than the single day on which it was authored: it proposes a player consumption loop, creator workflow, Workshop publication, IDE separation, shared operation center, and in-game workbench integration. Its checkbox status and dated execution notes indicate that several slices landed, including UGC query/subscription actions, target-profile installation, templates, composition assembly, and publishing receipt behavior. Those checkboxes are source-adjacent historical evidence only. They do not certify current Windows behavior, live Steam access, current subscription semantics, or completion of the open UI/IDE tasks.

The plan's initial goal and task names treat Studio as the one GUI that combines Discover, Library, Create, Workspace, and Workshop. The October 20 approved decision splits those workflows among Launcher, Studio, and IDE but retains the shared operation service and semantic model. This is an evolution of the product boundary, not abandonment of the full-stack lifecycle: consume remains Launcher-owned, creation/composition/release remains Studio-owned, and source editing/developer operations become IDE-owned. The same design states that opening a creator workspace cannot change the player's selected composition, a useful invariant confirmed separately in current code review.

Two vocabulary/identity conflicts remain material. First, the October 15 design treats “Composition/profile” as a durable user object separate from its root Packagepack and leaves that as an open design question. Later owner direction says “composition” is only an informal synonym for a playable Packagepack, not another identity. Current code still contains a separate `Composition` record and a `default` seed; this is a documented intent/implementation mismatch, not resolved by the October 20 product split. Second, the plan's Composer boundary was initially interpreted as Rust-free. Later owner clarification allows Cargo-backed composition of existing artifacts and manifests, while reserving Rust source authoring for Developer. The plan's phrase “Studio creates and composes content” does not specify that boundary and must be read with the later clarification.

Provider and distribution claims also have scope limits. The design records an owner-approved choice of Steamworks `ISteamUGC` for remote queries and subscription state while keeping local authoring available offline. This defines a provider contract, not Steam Workshop's semantic authority: later owner direction places canonical typed identity in Vapor's Registry catalog and uses Identity to authorize. Steam tags can aid discovery but do not enforce Vapor's content taxonomy. Likewise the lifecycle plan excludes publication for that pass, while later authorization allowed real public Workshop testing. These decisions apply at different levels and dates; neither should be generalized into a permanent ban or blanket publication policy.

**Disposition:** the two plans and the October 20 product-decision record were read together. Their durable requirements are one shared lifecycle/service, stable identity/provenance across discovery-to-release, explicit ownership by user role, source/play-state separation, recoverable long-running operations, and actual staged-artifact review before publishing. Their dated product labels, separate Composition identity, early Composer interpretation, plan-specific no-publish constraint, and completion checkboxes are not current truth without corroboration. Current code and the later owner decisions take precedence.

Relevant records: [October 14 repository design](</home/leslieghf/Vapor/Vapor-Client/docs/superpowers/specs/2026-10-14-vapor-repository-boundaries-design.md>), [repository migration plan](</home/leslieghf/Vapor/Vapor-Client/docs/superpowers/plans/2026-10-14-vapor-repository-boundaries.md>), [October 15 lifecycle design](</home/leslieghf/Vapor/Vapor-Client/docs/superpowers/specs/2026-10-15-vapor-studio-full-stack-content-lifecycle-design.md>), [lifecycle implementation plan](</home/leslieghf/Vapor/Vapor-Client/docs/superpowers/plans/2026-10-15-vapor-studio-full-stack-content-lifecycle.md>), and [October 20 product-surface decision](</home/leslieghf/Vapor/Vapor-Client/docs/superpowers/specs/2026-10-20-vapor-product-surfaces-decision.md>).

## 6. Player–Composer–Developer workflow-boundary pass (October 22 onward)

The owner-approved design establishes three nested workflow depths, not persona/security roles: Player, Composer and Developer. Composer uses Rust/Cargo for composition and may edit composition metadata without authoring Rust source; Developer owns source authoring. Tool readiness and external authority are independent facts. It also requires source workspaces to stay out of the player Library, makes workspace discovery explicit and asynchronous, and replaces the single global operation lock with resource-aware scheduling. These are direct responses to reported source/project conflation, long refresh stalls, uneven role promotion and a Studio whose Composer and Developer tools were mixed together. The design is kept as a local project artifact; the checked-in parent [implementation plan](</home/leslieghf/Vapor/Vapor-Client/docs/superpowers/plans/2026-10-22-workflow-boundaries.md>) points to that artifact rather than embedding it in the repository.

The plan was recorded by parent commit `058775e` and has several real partial implementations. `WorkflowTier` classifies public actions; service snapshots expose tiers/readiness; local artifact inventory is distinct from source-workspace discovery; workspace scanning runs asynchronously and supports cancellation checkpoints; an operation registry holds concurrent operation records and resource-conflict keys. However, a conflict is currently rejected with an “operation can start later” explanation; it is not retained in a queue. The owner asked for queueable actions, so conflict detection is not the promised scheduler. Service snapshots still perform Superworkspace discovery on the serialized request path, and scan cancellation is only between some stages. The plan's tests and full end-to-end cross-platform gates remain unchecked. See [workflow classification](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_domain/src/actions.rs#L388-L505>), [snapshot operation projections](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_protocol/src/state.rs#L68-L120>), and [current scheduling/refresh findings](current-state-semantic-cross-reference.md).

The UI migration is materially incomplete: the current Studio still exposes Create/Compose/Projects/Share without true progressive visibility; content-creation actions classify both metadata-only packs and source-bearing content as Developer, while the owner allows Cargo-backed composition at Composer level. The four-value installation `VaporRole` continues to provision a common developer environment for non-Player roles; it is not the three-level workflow model or authorization. This is exactly the kind of boundary duplication the design aimed to remove, and source evidence shows the conceptual classifier was added before the product surfaces and readiness bundles were made coherent.

Several clauses were later superseded. The plan says preserve/migrate user data unless reset is authorized; the owner later explicitly permitted fresh alpha state and local userdata removal. It says manual/local and Auto-Install semantics retain their previous behavior; the owner later defined Auto-Install as automatic version updates and lifecycle/unsubscribe ownership when unused. Its persistent Composition object must be reconciled with the later direction that Packagepack itself is the playable composition identity. These do not invalidate the nested workflow model; they mean its lifecycle and persistence assumptions cannot be implemented verbatim.

**Disposition:** retain the approved nested workflow levels, separate readiness/authority, source-versus-Library distinction, service-side action validation and nonblocking independent work as current product invariants. Treat queued conflict execution as not implemented; treat the UI/role/tool mapping as partial; and replace the outdated persistence, Auto-Install and separate-Composition assumptions with later owner decisions. The plan is not complete merely because its first three task groups have checked boxes.
