# Vapor Content-Graph Design Crosswalk

**Observed:** 2026-10-26. This crosswalk compares the untracked [October 24 content-graph design](</home/leslieghf/Vapor/Vapor-Client/Vapor/docs/superpowers/specs/2026-10-24-vapor-content-graph-design.md>) and [implementation plan](</home/leslieghf/Vapor/Vapor-Client/Vapor/docs/superpowers/plans/2026-10-24-vapor-content-graph.md>) with current source, earlier architecture documents, and the owner's later clarification in this conversation. The two design files are working drafts, not a signed-off implementation contract. They have no Git history in the current checkout; the owner definitions are conversation evidence, not an approval record for every proposed edge rule or task.

## Direction that is settled by the owner

The vocabulary is exactly ten content kinds unless the owner approves an evidence-backed change: Packagepack, Enginepack, Gamepack, Modpack, Engine, Game, EngineMod, GameMod, ExtensionMod, and Crate. Packs are typed manifests over content, not general-purpose source-code containers. The content artifacts are independently identified and distributable; their compiled library/module payloads are composable under Vapor's pinned toolchain. Packagepack is the playable root, and “composition” is an informal synonym rather than another authored kind. A Packagepack may deliver a finished target executable so the player does not compile Rust.

The kind boundaries express product/ecosystem roles rather than programming-language limits. Engine and EngineMod provide reusable engine/API capability; Game and GameMod express game behavior/content; ExtensionMod is a mod of a mod and must target a valid mod generically. Crate is ordinary Rust code managed as Vapor content, usable without an Engine/Game stack. Packs may expose optional additions or mutually exclusive paths; membership does not imply simultaneous compatibility. Mandatory targets, optional dependencies, alternatives, cardinality, conflicts, and compatibility are distinct dimensions.

The owner also made clear that Composer may use Cargo compositionally, including Cargo metadata, without authoring Rust source. Developer owns code authoring. That distinction must not be inferred merely from the `Crate` kind or from whether a manifest contains a Cargo path.

## Representation question the draft leaves unresolved

The draft describes Packagepack as one identity/release with editable source and runnable executable projections. That is compatible with the owner's requirement that players receive a ready-to-run executable and creators can edit/fork the Packagepack only if “source” is represented as references/provenance to separately identified content and source workspaces, rather than by putting all constituent content inside every pack. The wording “encompasses the source” is not enough to decide whether a Packagepack release contains source payload, references source releases, or resolves source from a workspace/registry. The draft simultaneously says packs are manifests and calls source and runtime projections part of the Packagepack release. That boundary needs an explicit artifact/identity contract before implementation: what Workshop uploads, what a player downloads, what a Composer acquires, and how the editable source graph resolves to the executable.

This is a genuine owner-definition seam, not a reason to invent another content kind. The crosswalk does not resolve it on the owner's behalf.

## Current implementation compared with the direction

The current `ContentKind` enum already contains exactly the ten names and canonical manifest spellings. `DependencySpec` has only an ID, version range, and optional Boolean. Kind rules are encoded in static parent/child tables; named relationships are strings such as `engine`, `game`, and generic `dependency`. The graph checks missing dependencies and member kinds. Packagepack resolution requires exactly one effective Engine and Game, but the resolver traverses the authored required edges and omits optional edges; it does not provide the proposed selected-alternative, explicit conflict, or feature-requirement model. The generic validator does not validate every nested pack's own shape. These are concrete mismatches with the user's richer graph semantics, not evidence that the current ten-kind vocabulary is wrong. [Content kinds and edge rules](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_content/src/content.rs#L30-L243>); [graph validation and Packagepack projection](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_content/src/resolution.rs#L110-L240>).

The ten-kind helper matrix makes the gap concrete. These are current direct-edge and root/target rules, **not** a claim that one validator enforces them all end to end:

| Kind | Direct child kinds allowed by shared helper | Required role/target rule present in code |
|---|---|---|
| Packagepack | All kinds except Crate, including nested Packagepack | Authored `engine-choice` and `game-choice`; resolved root needs exactly one Engine and one Game across its graph |
| Enginepack | Engine, EngineMod, nested Enginepack | `engine` choice; pack graph needs exactly one Engine |
| Gamepack | Game, GameMod, nested Gamepack | `game` choice; pack graph needs exactly one Game |
| Modpack | EngineMod, GameMod, ExtensionMod, nested Modpack | No required slot; pack graph must contain at least one mod |
| Engine | Any kind under the direct-child helper | No explicit target cardinality |
| Game | Engine or Crate | Exactly one direct Engine target |
| EngineMod | Any kind under the direct-child helper | Exactly one direct Engine target |
| GameMod | Any kind under the direct-child helper | Exactly one direct Game target |
| ExtensionMod | Any kind under the direct-child helper | Exactly one direct target whose kind is a mod |
| Crate | Crate only | No explicit target cardinality |

Two consequences are easy to miss: Engine/Game/mod target requirements are split between author-manifest validation and graph validation rather than carried as a typed edge contract; and the current helper allows a Pack to contain another Pack even though root-level cardinality is counted over the flattened resolved graph and nested Packs are not independently revalidated. The code therefore has several meaningful constraints, but not yet the author's intended recursive Pack-selection semantics.

There is also an important two-graph seam. Current authored Vapor edges identify semantic content; Cargo separately resolves the physical Rust build graph. The application-level build/package operation builds the workspace and then asks the provider to stage one selected artifact. That provider copies the selected artifact root and its declared executable/library outputs; it does not synthesize Cargo dependencies from all Vapor graph edges. Existing source analysis finds no invariant that proves each semantic constituent was actually linked into the produced executable. That means the current architecture has recognizable layers, but their join is partly author-maintained and currently under-specified. [Existing current-state trace](current-state-semantic-cross-reference.md#workshop-content-publishing-uses-a-separate-workspace-build-and-copy-pipeline).

Install preview and install execution are also separate graph traversals. `preview_install` delegates to the provider-neutral `resolve_install_plan` with a `LocalInstallProvider`, and the plan validates a complete Packagepack graph before reporting readiness ([shared preview entry](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content.rs#L1423-L1437>), [shared plan validation](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_domain/src/install_plan.rs#L125-L223>)). `install_composition` uses that preview to discover/acquire root Workshop seeds; it then calls `content::install`, whose provider path runs a second recursive `install_selector` with its own traversal and per-artifact checks ([application orchestration](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_application/src/content.rs#L534-L545>), [execution entry](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content.rs#L830-L868>), [execution resolver](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content.rs#L1772-L1900>)). The current selection branches mostly mirror source precedence, but execution validates each manifest's relationship cardinality and each selected edge; unlike preview, it does not validate the flattened resolved graph through `validate_content_graph`. A constructible example shows the distinction: a Packagepack can declare Engine A and Game G in its required slots, while G declares its required Engine as B. Each manifest satisfies its own local role count and every selected edge is permitted; recursive execution can install both engines. The preview sees two effective Engines in the flattened Packagepack graph and blocks it. Thus preview readiness is not an executable-plan contract, and direct install can bypass a graph-level Packagepack invariant. This is a source-proven policy discrepancy, not a reproduced run. `install_plan.rs` has no in-file tests; adjacent application tests cover Workshop dependency-request selection and root-selector normalization, not preview/execution parity or partial-failure recovery. The audit only inspected test definitions and did not run them.

Execution is also incremental rather than visibly transactional. It installs dependencies recursively before their parents; each `install_package` replaces/copies the installed tree and writes a per-artifact lock and receipt, while the overall content index is saved only after the recursive operation returns successfully ([dependency-first calls](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content.rs#L1804-L1898>), [tree, index-record, lock and receipt writes](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content.rs#L2092-L2147>), [final index save](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content.rs#L830-L868>)). If a later node fails, earlier filesystem side effects can remain without the final index update. The audit has not simulated this failure sequence, so the exact recovery behavior and whether orphaned artifacts are reconciled elsewhere remain open.

The package path sharpens that distinction: `package_for_targets` stages one discovered `ContentArtifact`; it copies that artifact's authored root, looks for already-built outputs named in the artifact, copies them into target-specific `bin/` or `lib/`, and writes a one-role deployed manifest. It is a packaging/staging operation, not the Cargo build or the semantic-graph-to-linker step. A missing declared output is an error directing the caller to `content build`; the source shows no automatic recursive build of semantic dependencies in this function ([single-artifact package entry](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content/packaging.rs#L30-L125>), [artifact root and output staging](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content/packaging.rs#L250-L350>), [deployed manifest validation](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content/packaging.rs#L560-L620>)). The separate Cargo reconciliation API checks direct normal Cargo edges only when the resolved root is a `Crate`; its own documentation limits the slice to that case. Current in-tree search finds definitions and Core exports but no Client-service consumer, so it is not the Composer's active generic content-link pipeline ([Crate-only reconciliation](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/cargo_reconciliation.rs#L1-L180>), [repair boundary](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/cargo_reconciliation.rs#L235-L310>)). This is a confirmed integration gap between two implemented subsystems, not proof that no manually authored Cargo package can work.

### The basic starter creates content metadata, not a playable build

`source init basic-content` writes a Rust workspace containing an Engine binary, a Game library, and a Packagepack manifest directory. Its Cargo workspace is built around the Engine and Game; the Packagepack is intentionally not a Cargo member. The generated Engine binary only prints the Engine title, and the generated Game library exports its identity plus the Engine's identity; it does not install gameplay into that executable ([initializer and workspace templates](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/source.rs#L94-L195>), [Engine/Game/Packagepack templates](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/source.rs#L240-L357>)).

The generated README's `content deploy ... --select` command therefore demonstrates source validation, graph selection, and local deployment mechanics, not a runnable game ([generated workflow](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/source.rs#L199-L228>)). The book describes host-only deploy as a “local proof,” which is too broad for this starter unless read as a proof of that limited deployment path ([Packagepack guide](</home/leslieghf/Vapor/Vapor-Client/Vapor/docs/books/vapor/src/concepts/packagepacks.md#L22-L31>)). The owner's later definition sharpens the gap: a Pack remains a typed manifest, while a completed Packagepack release carries a compiled executable tied to editable sources. This generator derives no such executable. Do not misread that contract as requiring the Packagepack manifest itself to become a Cargo crate.

The generated workspace also uses a narrower naming grammar than hand-authored manifests: scaffolded organization/workspace slugs reject underscores, while accepted manifest names allow them. That limits collision cases for this generator, but does not make the wider manifest identity grammar injective under the package-staging slug function described below ([scaffold validation](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/source.rs#L451-L470>), [manifest grammar](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/manifest.rs#L537-L590>)).

### Package staging has identity-collision and source-copy hazards

Two independent properties of the shared package path matter beyond the Crate output gap:

- **Distinct IDs can map to one package directory.** `VaporId` accepts any non-empty string without whitespace, while `slug` preserves only ASCII letters, digits and `-`, mapping every other character to `_`. The package directory is `output/content/packages/<slug(id)>`; non-dry packaging calls `reset_directory` on that path before staging. The source-root parser allows underscores in organization/workspace/content names, so hand-authored workspaces can define distinct IDs such as `org_a/game/x` and `org/a_game/x`; both slug to `org_a_game_x`. Sequential packaging from those roots shares one output directory, and the later package removes the earlier staged tree ([ID validation](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_content/src/identity.rs#L8-L42>), [manifest-name grammar](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/manifest.rs#L537-L590>), [package key and replacement order](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content/packaging.rs#L84-L125>), [slug and destructive reset](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content.rs#L2451-L2480>)). The workspace-scaffold command is narrower and disallows underscores in its generated organization/workspace slugs ([scaffold validation](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/source.rs#L451-L470>)); this reduces risk for newly generated roots but does not make the accepted manifest grammar or shared on-disk key injective.
- **Copy follows source symlinks.** `copy_tree` calls `fs::metadata`, which follows a symlink, then recursively traverses directory targets or copies file targets. The packager excludes `.git`, `target`, and `output` by lexical source-relative name but performs no symlink rejection or resolved-target containment check. A source-tree symlink can therefore bring external files into a staged artifact; if the creator publishes that output, unintended files could be included. This is an exposure path, not evidence that a real secret was staged or uploaded ([copy implementation and exclusions](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content.rs#L2422-L2453>), [Workshop build/package route](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_service/src/session/workshop.rs>)).

The non-dry package path has a separate partial-failure property: it deletes the previous staged directory and creates a replacement before `stage_deployed_artifact`, fingerprinting, and receipt writing complete. An error after reset can leave an incomplete package and no prior staged output to fall back to. The dry-run path uses an app-root temporary directory with Drop cleanup, but that does not make the final output replacement atomic. The Oct 20 `a600804` test verifies only temporary-directory confinement and cleanup; it does not exercise replacement failure, symlink handling, or colliding identities. The package/reset order dates to the initial Oct 19 packaging implementation (`d7e21dc`); later commits addressed temporary staging location and Windows library-name discovery, not these properties. No destructive package, symlink, or failure test was run.

### Crate lifecycle — scaffolded, but not yet a distributable link input

The live Crate path has three distinct partial mechanisms, and their presence can make the whole lifecycle look more complete than it is:

1. **Scaffold:** `Crate` maps to a Rust project with `crate-type = ["rlib", "staticlib"]` ([template](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/source.rs#L395-L449>)). But its manifest writer intentionally emits no `libraries = [...]` entry for `StaticCrate` ([writer](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content/authoring.rs#L2342-L2363>)).
2. **Package:** build-and-package first builds the whole workspace, then stages the selected content. The stage copies the content root and only copies compiled outputs explicitly named in `binaries`/`libraries`; the default exclusions are `.git`, `target`, and `output` ([operation](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_application/src/publishing.rs#L113-L143>), [staging](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content/packaging.rs#L275-L345>), [exclusions](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content.rs#L2451-L2453>)). Thus the generated Crate has a staticlib build target, but its default staged Workshop artifact does not declare or include that output. The copied root can still contain `Cargo.toml` and `src`; source is not separated from the deployed payload by this packaging path. This conflicts with the Vapor book's broader statement that staged content “is not a Cargo checkout” ([book claim](</home/leslieghf/Vapor/Vapor-Client/Vapor/docs/books/vapor/src/authoring-content.md#L55-L66>)). The source evidence does not prove that every content root is a full Cargo checkout, but it does prove the packager does not remove Cargo/source files when they are present.
3. **Cargo composition:** Core's `CrateCargoReconciliation` checks direct Vapor dependencies of a locally available Crate against Cargo metadata and can add missing path dependencies, while refusing to overwrite conflicts ([verification](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/cargo_reconciliation.rs#L130-L234>), [repair](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/cargo_reconciliation.rs#L236-L302>)). Separately, the generated application realization takes only the selected Engine and Game, adds those two local Cargo packages to a generated manifest, and rejects all Mods; it does not project resolved Crate nodes into the generated Cargo graph ([selection](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/cargo.rs#L363-L398>), [Engine/Game-only realization](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/cargo.rs#L442-L498>)). These two public Core facilities have no call sites in the Client/application/service crates in this checkout; Core only re-exports them. The normal authoring package path therefore builds what is already expressed in the workspace's Cargo manifests but does not prove that the resolved Vapor graph matches that Cargo graph.

This yields a source-confirmed gap against the owner's target: **Crate source, Crate's prebuilt static payload, and a Composer's locally generated link graph do not yet form one demonstrated path.** Current staging can carry source and optional runtime-library files; current reconciliation works with local Cargo package paths; current app realization wires only Engine and Game. The host target's `lib*.a`/`.rlib` suffix handling added for Windows GNU in `6efe082` improves output discovery only when a library name is declared; it does not connect those archives to composition linking. Do not treat “supports `staticlib`,” “can stage `.a`,” and “can compose downloaded Crates without source” as equivalent capabilities.

## Draft plan assessment

The draft's broad decomposition is well aligned: first classify edge roles; then model compatibility, conflicts, cardinality and optional choice; then represent pack paths; then connect source and runnable projections; finally validate examples across all ten kinds. It correctly says not to preserve current behavior merely because it exists, holds the content vocabulary fixed, and leaves UI/IDE/Rhai code-generation as separate workstreams. The examples it proposes—optional Enginepack/Gamepack members, mutually exclusive Modpack paths, Create-like EngineMod/GameMod/ExtensionMod chains, and standalone Crate—exercise materially different semantics.

Before this plan is safe to implement, its acceptance criteria need a canonical table for each kind describing: required targets; optional edges; alternative groups; maximum/minimum cardinality; compatibility and conflict scope; inclusion in each pack type; source/build artifact outputs; and whether the relationship participates in runtime, compile/link, or editor-only closure. The Packagepack source/runnable ownership question above must be answered first. Otherwise Tasks 1–4 risk encoding different interpretations of the same word “dependency,” and the test fixtures will simply ratify whichever interpretation the first implementation chooses. No code changes are authorized by the draft itself.

The implementation plan remains wholly future work: all task checkboxes are open, and its managed tests, target-matrix package proof, and example publication claims have not been performed in this audit. The surrounding owner request is to plan before implementing and obtain review of the technical plan. This crosswalk therefore records design alignment and open decisions; it does not execute the plan.

## Disposition

- **Keep fixed:** the ten-kind vocabulary and the user's role distinctions; Packagepack as the playable root; packs as typed manifests; compiled content as separately meaningful artifacts; Composer as Cargo-backed composition without Rust-source authorship.
- **Do not assume implemented:** optional/alternative/conflict resolution, full pack-path selection, complete all-kind examples, source/runtime projection identity, or proof that the Rust Cargo graph matches the Vapor semantic graph.
- **Resolve before coding:** the Packagepack source/executable payload and identity relationship, then the per-kind edge/cardinality/selection table and the semantic-to-Cargo linking invariant.
- **Status:** current implementation compared at the cited interfaces; draft intent cross-referenced to the owner definitions and older architecture. No builds, tests, deploys, formatting, or source edits were performed.
