## Read this first

For the joined latest-state view of content identity → source/build → Pack → Workshop → Library → Packagepack launch, plus the separate-but-related Rhai/Rust/capability boundary, start with the [current-state semantic cross-reference](current-state-semantic-cross-reference.md). This atlas remains the broader map across products, services, tools and docs.

Vapor is not a blank slate, and its products are not wholly separate implementations. A canonical local Client service, shared protocol, domain actions, ten-kind content vocabulary, resolver, operation reporting, product frontends, semantic editor model, managed language-server path, Steam UGC integration, Registry service, and documentation system exist in source. The central issues are that these foundations are **parallel rather than singular**, **incomplete at semantic seams**, and **described inconsistently by code, UI, and docs**.

The clearest contradictions at this snapshot:

1. The owner defines Packagepack as the playable-selection identity and its release as including a ready executable. Current state still has a distinct durable Composition object; fresh state creates and activates a special `default`/`Default` Composition before the app seed fills its root.
2. The owner wants packs to be typed selection manifests and dependency relations to represent alternatives, requirements, constraints, cardinality, and build use. The implemented resolver mostly walks required edges, skips optional edges, chooses a satisfying version per edge, and validates pack shape afterward.
3. The current content lifecycle uses role-specific manifests from authoring through packaged artifacts. But `vapor_core` still exports a Vertical-Slice-0 generic `[content]`/`Vapor.toml` local catalog and Cargo realization path, and the Steam distribution still requires and ships `vapor-ide-host`, whose only protocol reads that old catalog. The current IDE uses the service-native workspace/content API; no product caller for the shipped host appeared in the source search. This looks like a packaged legacy path, not the current Library implementation.
4. Books still describe Packagepack as metadata-only and Composition as a separate player object. Some roadmap pages make stale broad “unimplemented” claims: Workshop flows exist, and Loo-Cast has a bounded Rhai compile/execute path, though neither fact proves the full intended lifecycle or capability architecture.
5. Loo-Cast’s package-level Engine→Game composition exists, but source/artifact ownership is inverted: `loo-cast-game` is a 17-line wrapper while the Engine package owns the 158-file `spacetime_engine::game` source subtree; Engine physics also names a Game schedule. The root’s developer-run profile targets the now-removed Engine binary, and the in-game F2 editor does not consult Vapor role. These are separate current-state seams, each detailed below.
6. The Workshop-configured wheel example's Vapor graph and its Cargo composition are two descriptions: the manifest declares Engine/Game/Mod/Crate identities, but its Rust entrypoint hardcodes the Game and Mod installer calls. It proves static linking and gameplay, not graph-driven composition generation or current public Workshop availability.
7. The main `vapor` CLI has service-backed workflows, but the nested `vapor sdk` command is a mixed-generation subsystem: workspace Cargo/status/deploy and first-party root packaging/publication have direct SDK-Core implementations, while many typed per-content author/build/package/publish commands still return `not_implemented`. Its workspace sync also remains a direct manifest-driven file generator with weaker path containment than the Client provider. The single-service product direction is not yet the only command route.
8. Installer has an app-root player receipt, user-data role state, managed tools split across user data and app root, and a second legacy app-root setup implementation. In the current GUI promotion path, the role can be persisted without checking the returned readiness aggregate; first-launch continuation then checks role and error fields but not the readiness booleans.
9. Diagnostics capture and server ingestion are separate implemented halves: the Client's future HTTP transport always reports unconfigured, while the server accepts anonymous uploads. The local capture includes paths and arguments excluded by the server schema; upload privacy projection, retention and abuse controls remain unresolved.
10. The current docs books contain the richer task/status navigation the product needs, but the deployed root generator flattens shell/design material and chooses rendered HTML versus raw Markdown based on whether `mdbook` happens to exist. The uploaded bundle was accepted, but the stale deployment record cannot identify the currently served tree.
11. “Shared console” now means at least four distinct layers: Loo-Cast’s synchronous ECS command runtime and F2/stdin frontends; the Vapor service’s typed `ClientAction` command vocabulary; shared Vapor record/history/filter/view code; and CLI/GUI renderers. The game and Vapor service do not share execution authority or event transport. Their histories have separate caps (512 game overlay records, 4,000 GUI view records); GUI widget rows are virtualized, but filtered-index rebuilding still scans the bounded history. This preserves the game’s powerful live-world authority while showing that renderer reuse has not fulfilled the broader one-console direction. See the [latest console cross-check](loo-cast-vapor-semantic-diff-review.md#latest-state-console-trace--game-command-runtime-versus-vapor-operation-console).
12. The shared-console design and code are not aligned in every field or scope: its canonical record explicitly names origin and kind, but the shared type has neither as typed fields; current GUI origins are conventions in a generic field. The separate command-console spec anticipates extensible typed registrations and one catalog, while current commands are a fixed small list and IDE/Studio parse/dispatch in separate code. The wider user request for a shared egui toolkit/preview workflow remains unplanned; the Oct 22 spec explicitly deferred full toolkit work. See the [design-to-code reconciliation](loo-cast-vapor-semantic-diff-review.md#design-promises-against-the-october-25-implementation).
13. The IDE’s semantic workbench now has selectable Rust declarations, field-level projections, special Rust tree ordering/labels, canonical module creation, and convention diagnostics. Its nine-category scaffold applies to detected Cargo `src` trees, not a Vapor `Crate`/content role; the shared `systems.rs` starter and item templates assume Bevy. Layout diagnostics are IDE-only warnings; service scaffolding guards creation of one new module/parent update, but it does not enforce the convention across existing source, CLI, builds, or CI. The workbench is semantic visibility and guarded authoring, not yet Vapor-governed Rust architecture. The intended policy scope and framework-neutral versus Bevy-specific rules remain unresolved. See the [Rust semantic workbench cross-check](loo-cast-vapor-semantic-diff-review.md#october-25--the-semantic-ide-teaches-rust-structure-but-does-not-govern-it-yet) and [latest-state Rust governance cross-check](current-state-semantic-cross-reference.md#rust-workbench-semantic-visibility-exists-crate-policy-and-authority-do-not).
14. The semantic workbench’s common node/range/diagnostic machinery spans Rust, TOML, Rhai and XML, but their authority differs: authored TOML manifests use the shared `ContentKind`/`AuthoredContentManifest` model; Rust depends on Rust Analyzer plus syntax projection; Rhai is outlined and parse-checked without execution; XML is a generic outline without schema. The Oct 23 plan’s adapter work is therefore partially delivered, with richer Vapor-model integration than a format checklist suggests and no parity of editing/execution. See the [adapter authority comparison](loo-cast-vapor-semantic-diff-review.md#october-25--the-semantic-model-is-shared-adapter-authority-is-intentionally-uneven).
15. `vapor_gui_core` is real and already reused for editor, console, panel, icon, semantic and workspace-tree capabilities, but it is not yet the broad UI toolkit or preview lab the owner described. Layout and most product-specific controls remain in frontends; the IDE composes raw egui panels directly, and the core mixes visual controls with semantic adapters. See the [UI toolkit state review](loo-cast-vapor-semantic-diff-review.md#october-25--vapor_gui_core-is-a-useful-seed-not-the-promised-egui-workbench-toolkit).
16. GUI launch surfaces are already separate process-image targets (`vapor-launcher`, `vapor-studio`, `vapor-ide`, `vapor-installer-gui`, plus chooser `vapor-gui`) and Steam Entrypoint selects them by sibling executable name. The remaining coupling is one Cargo package/host/router, cross-repo UI dependencies, and an unrestricted `--mode` override; source staging does not prove current depot contents or runtime launch. This corrects the prior “one executable” description. See the [binary/host boundary cross-check](loo-cast-vapor-semantic-diff-review.md#october-25--gui-products-have-distinct-binaries-but-share-one-host-package-and-overridable-mode-router).

Entrypoint pre-start and frontend service connection are overlapping authorities: most routes call `--ensure`, but Installer is omitted there and connects-or-starts the same service itself; chooser is service-free. The service exits after 15 seconds without clients or active operations, not on Steam-close notification. ## Owner model to compare against

This is **Owner direction** from the conversation, condensed without changing it:

- The fixed vocabulary is Packagepack, Enginepack, Gamepack, Modpack, Engine, Game, EngineMod, GameMod, ExtensionMod, and Crate. No additions or removals without strong justification and explicit approval.
- Packs are typed manifests/selectors; they do not contain constituent source or compiled libraries. Packagepack is the root of a playable selection. “Composition” is informal language for that selection, not a separate content kind.
- Content owns implementation and reusable compiled artifacts. Packagepack is unique among packs because its release also includes a finished, linked executable. Player install must not compile the game.
- Composer combines existing content and packs into packs. It may use Cargo compositionally, edit Cargo.toml or other composition metadata, and link prebuilt libraries; it does not author Rust source or build constituent source. Developers or trusted CI build reusable content libraries.
- Dependency semantics must distinguish mandatory targets, required/optional dependencies, selected alternatives, compatibility, conflicts/exclusions, cardinality, and build/link use. Pack members may represent incompatible paths.
- Rust versus Rhai does not define Engine versus Game. Engine owns reusable capability and mechanisms; Game owns game-specific behavior/content. Both may use Rust; scripts compose through host APIs.
- Vapor has one semantic core/service. Launcher, Studio, IDE, Installer, chooser, and CLI are separate user-facing surfaces over common lifecycle rules.
- Player → Composer → Developer is a nested workflow/skill progression; it is not automatically the same as local install roles or remote authorization.
- Source workspace, acquired Library content, Workshop subscription, Packagepack selection, and local installation are related but distinct projections.

For the deeper proposal and task sequence, see the [owner-review architecture draft](/home/leslieghf/.codex/.chatgpt-projects/g-p-6ab69f33d17481919fb92a0c5592210c/artifacts/vapor-ecosystem-architecture-plan-draft.md), [content-graph design](/home/leslieghf/Vapor/Vapor-Client/Vapor/docs/superpowers/specs/2026-10-24-vapor-content-graph-design.md), and [implementation plan](/home/leslieghf/Vapor/Vapor-Client/Vapor/docs/superpowers/plans/2026-10-24-vapor-content-graph.md). Those are **Proposed** planning material; this atlas does not silently promote their open decisions.

The UI calls the former, while the legacy installer CLI still exposes the latter. Source proves duplicated ownership and different storage; it does not prove which path caused any particular Windows promotion error or which binaries were present on the user's machine.

There is also a readiness-postcondition hole inside the newer path. `DeveloperEnvironmentStatus::is_ready()` exists, and maintenance diagnosis uses it, but role promotion ignores `report.status` after reconciliation and persists the higher role whenever each installer call returned `Ok`. ### 3. Shared service, operations, logs and cross-frontend behavior

Frontends send typed ClientAction values over vapor_client transport. Protocol snapshots carry host facts, persistent state, available actions, operations, and catalog/composition/Workshop state. GUI routes Chooser, Installer, IDE, Launcher/Play and Studio product modes ([router](/home/leslieghf/Vapor/Vapor-Client/Vapor-GUI/crates/vapor_gui/src/lib.rs#L1), [protocol](/home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_protocol/src/state.rs#L1), [service session](/home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_service/src/session.rs#L1)).

The protocol is a substantive shared product-state contract, not a thin independent DTO adapter: its eight current files re-export Client Domain actions/records, model broad snapshots and operation events, and carry LSP and semantic diagnostics on the same local connection. Some meaning is still flattened to strings (`kind`, local role, mode), while CatalogEntry carries both human-readable dependency labels and structured dependency facts; only the latter is suitable as typed lifecycle input. Exact protocol-version equality is required at startup and per request, although additive serde-defaulted fields can preserve compatibility when the protocol version is deliberately unchanged (as happened for dependency details at version 30). Each action response includes a full snapshot and is followed by a broadcast snapshot; the 32 MiB frame limit, eight-client limit, and 40 MiB per-client outbound queue imply a 320 MiB aggregate serialized-queue ceiling before other process memory. This may be a deliberate lockstep-depot design, but current source does not provide general independent client/service compatibility. Detailed evidence and limits: [protocol boundary review](loo-cast-vapor-semantic-diff-review.md#october-25--the-client-protocol-is-the-product-state-surface-not-a-thin-transport-dto-layer).

**Service-process verification exists but is host-scoped:** the current service integration target has 13 tests that spawn the executable, use the real IPC path, and check lifecycle actions, Workshop fixture flows, workspace-file event ordering, production run-configuration resolution and state persistence across restart. Fixture publish paths explicitly refuse external publication. These are stronger than session-only tests, but no Windows result, live Steamworks flow or whole Steam-depot launch is established by them; none were run in this pass. See the [process-test review](loo-cast-vapor-semantic-diff-review.md#process-level-tests-cover-the-service-boundary-on-one-host-not-the-shipped-platform-matrix).

**The service extraction did not replace the older Core as the implementation boundary.** The October 18 extraction added Client, Domain, Protocol, Provider, Application, Service and Content crates in one 85-file / +27,021-line commit (`f9e8b13`); October 19 moved a further operation set behind the service and removed 2,704 lines of the former Core CLI (`d7e21dc`). In the current manifests, Service still depends directly on both Application and `vapor_core`; Application depends on Provider, `vapor_core` and Steam; Provider depends on `vapor_core`, Content and Client Domain; SDK Core also depends on `vapor_core`. Core still exposes 32 public modules and 16,907 source lines. It is not merely a primitive value/model crate: it owns workspace and source discovery, toolchains, roles, installation, Cargo execution, Steam publishing, docs publication, profiling and other host operations. These imports are visible in the service's authoring/workspace/snapshot paths and Provider's Cargo, Steam, docs, release and launch implementations ([current manifests](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_service/Cargo.toml>), [Core facade](/home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/lib.rs#L1)).

There are also frontend bypasses. `vapor_installer_ui` directly calls Core for installation status, install, repair, uninstall and role transitions. The regular CLI's local-client deployment command directly calls Core, while most gameplay content actions use Client IPC. `vapor_sdk_cli` has its own direct SDK Core execution path. That leaves a real shared service for much of the Client lifecycle, but not one universal operation API for every product. The structure may be an intentional staged extraction; the source does not establish that Core's responsibilities have been reconciled or that its size is unnecessary. The precise finding is **layered but not yet converged ownership**: new application/provider/service layers call through the old broad Core, and selected frontends still bypass the service. The 68k-line Shared Vapor checkout figure is thus not all one service implementation; the current 16.9k Core and 16.2k Service are distinct, partly coupled owners. No runtime behavior or code-size necessity was inferred from these counts.

**Current public Core surface, module-level inventory:** `vapor_core/src/lib.rs` exposes 32 modules publicly and reexports APIs from most of them. They form a recognizable functional grouping, but not a narrow immutable kernel: (1) content identity/schema/adaptation—`authored_manifest`, `content`, `identity`, `manifest`, `local`, `resolution`; (2) installation and local capability—`installation`, `install`, `role`, `developer_environment`, `maintenance`, `uninstall`; (3) authored-workspace context—`workspace`, `superworkspace`, `source`, `ecosystem`, `development`, `run`; (4) native build/process/tool management—`cargo`, `cargo_reconciliation`, `toolchain`, `cross_target_toolchain`, `managed_tool`, `managed_process`; (5) product/provider integrations—`ide`, `ide_host`, `steam`, `registry`; and (6) host/operation/observability—`host`, `operation`, `profiling`, `tracy`. Several names expose explicit legacy or transitional scopes: `manifest.rs` labels its `Vapor.toml` shape Vertical-Slice-0; `local.rs` discovers that old local catalog; `authored_manifest.rs` and `identity.rs` are compatibility reexports; and `ide_host.rs` is a separate stdio host. This classification is an API-surface map, not proof that every module is unnecessary or that the groups should become crates. ### 6a. Thermal and combustion: a coherent slice with a two-level state model

The October 25 thermal subtree is 22 Rust files / 2,157 lines. Its earlier architecture note described the intended boundary unusually clearly, but that note was deleted on October 6 in `0e48843` (99 lines removed). Its major claims were compared with the current code rather than treated as present-day proof. The current module comments preserve much of the model; no thermal-specific automated test was found in the inspected engine test locations, and no runtime validation was performed.

**The reusable causal core is real.** `ThermalImpulse` is a signed energy message, `ThermalBody` owns aggregate temperature/capacity/cooling, `ThermalMaterial` owns SI solid properties, `CombustibleMaterial` owns ignition/extinction/transfer policy, `Fuel` owns remaining chemical energy, and `Combustion` is derived state. The game Heat Ray emits a localized `ThermalPointImpulse`, not a fire flag; the thermal systems derive ignition and combustion. Thermal visualization and flame presentation are separate from simulation. This supports a clean mechanism/policy split for the current vertical slice ([thermal domain](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/thermal/domain), [core plugins](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/thermal/mod.rs), [Heat Ray adapter](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/game/playground/items/heat_ray/mod.rs)).

**Spatial refinement is optional and semantically shared.** `ThermalField` is a local regular finite-volume grid attached to the semantic entity, not a per-manifestation copy. A marked `ThermalSpatialSample` supplies each manifestation's transform; runtime ownership maps it back to the semantic entity and the scale layer converts coordinates to metres. Heat propagation finds the closest pair of manifestation positions for each semantic pair, uses quadratic falloff, accumulates joules per target, then applies them to `ThermalBody`. Candidate discovery is explicitly O(n²), local-scene-only, and documented as replaceable. This is a useful mechanism contract, not a global USF distance/residency solution ([heat transfer](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/thermal/simulation/heat.rs), [field](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/thermal/spatial/field/mod.rs)).

**Confirmed authority seam:** aggregate and spatial state are both stored and both appear authoritative in different operations. Localized impulses update the struck cell and aggregate body by the accepted energy; internal conduction updates only the field; ordinary `ThermalImpulse`, ambient cooling, and combustion update only `ThermalBody`; then the spatial-output system projects any aggregate energy difference uniformly across every field cell. This preserves legacy aggregate gameplay behavior but erases spatial gradients whenever those aggregate-only mechanisms change energy. The architecture note explicitly described this as a compatibility bridge and said new localized systems must write the field directly. It is therefore a known transitional rule, not an accidental contradiction—but there is no single energy ledger and the rule is easy for future callers to violate. Combustion currently changes body temperature uniformly through that reconciliation rather than depositing its self-heat locally. The demo heat ray is localized; the combustion pathway is not ([aggregate evolution](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/thermal/simulation/energy/mod.rs), [combustion](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/thermal/simulation/combustion/mod.rs), [reconciliation](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/thermal/spatial/simulation/mod.rs#L94)).

**The injury adapter is intentionally game-owned and currently connected.** `ThermalInjury` is a reusable threshold/rate policy type, registered by the thermal plugin; `game::health::thermal_injury` converts aggregate excess temperature into generic `Damage` in the game Phenomena schedule. It is not a thermal-core consumer and does not sample the maximum local field temperature. This means a hot cell can trigger combustion from the field maximum while biological injury remains governed by aggregate temperature. The distinction follows the chosen compatibility model, but its user-facing meaning needs deliberate confirmation if localized heat is expected to injure a person at the hit point ([game adapter](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/game/health/thermal_injury/mod.rs), [schedule](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/game/mod.rs#L160)).

**History explains the model's maturity and limits—and a coverage regression.** `ebd9645` (September 12) introduced the systemic fire/health slice: aggregate body, fuel/material/combustion, thermal injury and derived flame. ### 7a. Worldgen means deterministic construction inputs today, not procedural worlds

The `worldgen` crate root is 444 lines across two files. The Engine README explicitly calls it experimental and says its descriptive catalogue is not live world construction ([README](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/README.md#L10)). The module implements a persistent-default `WorldSeed`, stable key/revision/field-separated sample seeds, exact-versus-procedural typed constraints with provenance labels, and a `SparseConstructionAtlas` keyed by stable phenomenon identity. Atlas queries compare conservative initial-position/radius bounds against a requested canonical chunk, return a conservative candidate when coordinate projection fails, and do not create ECS entities, chunks, residency or simulation state. Its BTreeMap iteration gives stable identity order, but every region query filters the full catalogue; this is a tiny sparse source index, not a spatially accelerated world database.

**The only current fixture consumer defines Earth and Moon as facts.** The fixture resolves both radii through `ConstructionConstraint::Exact`; its procedural fallback closures are not invoked. Centers, gravity, arrival direction and orbital elements are literal authored values. The fixed root seed therefore does not vary the current Earth/Moon body facts; it only supplies a deterministic input if a future recipe actually chooses `Procedural`. The fixture builds a two-entry atlas, selects an S+8 canonical context, constructs selected semantic celestial entities, then retains the source atlas in an unread `_source_facts` resource field. The source comments explicitly distinguish those initial authored facts from a live orbiting body's evolving position. This matches the user's physical-level Earth/Moon fixture direction and preserves an extension seam; it does not implement galaxy/planet/terrain generation ([fixture definitions](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/game/world/fixture/definition.rs), [fixture composition](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/game/world/fixture/scenery/mod.rs), [semantic body construction](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/game/world/fixture/scenery/celestial.rs)).

**The fixture's arrival resolver is a terrain-aware algorithm placed over terrain that is currently a sphere.** It searches eight deterministic arc-distance rings from 0 through 160 km, with twelve directions per nonzero ring; probes four points at a hull-derived 75–500 m radius; estimates a local normal and roughness; and prefers ≤18° slope, then ≤32°, before falling back to the best remaining candidate. It rejects candidates whose outer-shell sample is not within 0.25 m of the signed-distance boundary. The resolver therefore has a real bounded search and a real hull-aware placement transaction, but the current sphere field makes every sampled surface radial and smooth; the terrain-gradient/cave behavior implied by its comments is dormant. Once selected, placement offsets along the body-radial ray by hull support plus 0.75 m for a character or 25 m for a spacecraft, writes the canonical semantic position and current chart transform, zeros velocity/stops canonical motion, and queues a separate coverage-gated spatial transition. The code does not show this semantic spawn write waiting for collision realization before it occurs; coverage gates the queued interaction transition, not the initial position assignment. This is source behavior, not a runtime safety failure ([bounded spawn search](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/game/world/fixture/spawn.rs#L20), [placement and transition](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/game/world/fixture/player/mod.rs#L37), [bootstrap caller](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/game/world/fixture/player/mod.rs#L161)).

The provenance label is similarly coarse: `PhenomenonProvenance` stores one boolean for whether a phenomenon has authored constraints, while the fixture passes `true` for each body. It does not record per-field provenance, and the current body constructor does not resolve most values through the generic constraint API. This does not falsify the authored facts; it means the provenance component cannot answer which individual fields were authored versus generated if recipes later mix both sources. The retained source catalogue also has no reader in the current tree, so it is a lifetime-preserved input snapshot rather than a demonstrated live source-of-truth or query service. These are model-capacity observations, not runtime defects.

The worldgen files contain focused `#[test]` cases for stable/domain-separated sampling, exact constraints bypassing fallback, atlas boundary discovery, empty-region lookup without realizations, coarse discovery of fine facts, and seed-independent authored Earth/Moon data. However, these are not active test targets: `spacetime-engine/Cargo.toml` sets `[lib] test = false`, so the source annotations are not built into the unit-test harness. They describe invariants but provide no executable regression guard under the current manifest. They also do not cover procedural fallback world creation, catalog-to-streaming orchestration, terrain algorithms, or a full generated-world save/reload. No tests were run in this research pass. The owner’s requested division—authored physical facts where real worlds are deliberately fixed, deterministic procedural facts elsewhere, and potential unusual time/scale powers later—should not be collapsed into “worldgen already exists”: the extensible input/provenance substrate exists; the generative content algorithms and orchestration do not.

### 7c. Play is service-routed, but the executable/content binding remains a separate contract

The current Studio Play action is a real cross-layer route: protocol `CompositionAction::Launch` enters `ClientSession::start_composition_operation`; the service snapshots the selected composition and starts an asynchronous `studio-composition` operation; its worker calls `vapor_client_application::run_installed_composition_with_context`; the application obtains or repairs the installed graph, compares it with the composition's saved graph, then calls the provider to verify and prepare a Packagepack launch; the provider resolves the host target and launches the packaged binary while forwarding child output into the operation stream. Completion is returned to the service, which refreshes the catalog and records the operation outcome. The shared Client service therefore owns the frontend-facing action, lifecycle, and output channel; the application/provider remain in-process Rust layers called by the worker, not another independent daemon behind this action ([service dispatch and worker](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_service/src/session/composition.rs#L5-L130>), [operation execution](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_service/src/session/composition.rs#L560-L620>), [application launch and graph comparison](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_application/src/content.rs#L796-L860>), [provider graph and target resolution](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content/launch.rs#L115-L232>)).

This route has a phase/side-effect caveat: persisted installation state is cleared to `Unknown` at service restart, and the snapshot still enables Launch for a rooted selection not marked `OutOfDate`. The application launch helper then installs a missing graph or repairs an existing one; installation first downloads/imports missing root-seeded Workshop items. The service classifies that whole operation as `Running`, and the install/acquire functions do not receive the operation context; only the later game process is wired to stream output. Thus Play is capable of content acquisition and installation before execution, not just process launch. If installation succeeds but executable startup fails, completion still persists the installed graph/state and reports the Play operation as failed; installation is not rolled back with the failed launch. That may be intended, but the accepted user-facing install-before-play flow and first-launch Vapor role/tool setup do not by themselves decide whether content setup should be implicit on Play. No UI or Workshop operation was executed; see the [detailed source review](loo-cast-vapor-semantic-diff-review.md#october-26--play-can-acquireinstallrepair-before-launching-while-reporting-running).

The provider's installed-graph verifier checks that each required installed dependency is enabled, version-compatible, non-conflicting, valid under typed relationship rules and recursively present. It allows an absent optional edge, but validates an optional edge if that content is already installed. Packagepack launch then requires exactly one effective Engine or Enginepack and one Game or Gamepack, with the corresponding pack resolving to exactly one member of the needed role. This is a concrete typed graph check, but not the owner's envisioned first-class selection among mutually exclusive pack paths: all present optional dependencies participate in the closure, while branch choice is not represented in the launch request. The [release identity cross-check](current-state-semantic-cross-reference.md#what-looks-like-one-release-but-is-not-yet-one-contract) and [owner model table](current-state-semantic-cross-reference.md#the-premium-contentcomposition-model-durable-thesis-changed-vocabulary-unfinished-realization) detail this broader mismatch.

The runnable payload is checked separately from that graph. The provider reads the Packagepack manifest's runtime record for the current host and picks its first declared binary filename; it verifies that the file exists under `bin/<target>` and is a regular file. It does not prove that this executable was linked from the exact Engine/Game/Mod versions in the verified graph. The packaging provider stages already-built files from the managed `output/dev/<workspace>` tree, copies the full source project into the staged package, and writes target-to-filename runtime metadata. The stage receipt fingerprints the finished directory, but this route does not itself build the source or bind the executable to a Cargo lock/build receipt or source revision. Therefore a self-consistent installed manifest/dependency graph and a present host binary can still be two independently true facts rather than proof that the binary realizes that graph ([runtime staging](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content/packaging.rs#L275-L345>), [runtime target lookup](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/content/launch.rs#L532-L582>)). This is a source-level integrity boundary, not evidence of a mismatched published executable.

The child process call waits for the launched program to exit inside the background operation; the GUI can remain responsive because the service scheduled that call off the session thread, but the operation remains active for the game's lifetime and its console stream is coupled to that lifetime. Existing service tests exercise launch readiness, active-operation conflict/queueability and stale-install rejection using the fixture path. The provider launch module has no focused tests, and the process integration file has no real `CompositionAction::Launch` run; there is no source-level test here that acquires a real published Packagepack, proves its linked dependency graph, and closes its process/output lifecycle. No tests were run in this research pass. This separates three confidence levels: typed action and state gating are unit-tested; production graph/binary resolution is source-inspected; end-to-end packaged launch is not established by this evidence.

**A richer October 6 prototype was deleted two days later, but it also was not live world construction.** At `0e48843`, `worldgen` had a `PhenomenonRule` trait/registry, typed-but-erased snapshots, a sparse cache keyed by canonical spatial chunk + opaque `TemporalScale` label + epoch, +35-to-finer contextual evaluation, domain-separated seeded noise, and nine approximate built-in phenomenon families spanning cosmology, matter distribution, halo/galaxy/system, planetary body, geology/climate/hydrology, ecology and material substrate. Crucially, its own module header says those snapshots did **not** construct celestial identities, terrain, ecology or material state, and that Loo-Cast's authored fixture did not consume it. Its temporal scale was explicitly only a model-resolution label, not seconds, a timestep, a simulation clock or physical time travel. The full 1,382-line prototype was removed in `d806e3d` on October 8. The deleted [October 2 segmented-materialization design](https://github.com/GHF-Studios/Loo-Cast/blob/020877577d1c1c0f86b69a519b43d5af2dcea844/docs/superpowers/specs/2026-10-02-segmented-voxel-materialization-design.md) says it was approved and frozen before implementation at that moment. It treated materialization address, occupancy knowledge, dense samples, derived surface, presentation, collision and editing as separate state/capabilities; demanded compact uniform facts, no empty ECS manifestations, batched capability coverage, role-ranked work and telemetry. The October 6 cleanup deleted the design. Its approval is important historical intent, not a permanent veto over later owner-directed rework; the rows below compare the accepted 2026-10-02 target to the October 25 code.

| Design contract | Current source | Status |
|---|---|---|
| Address/semantic identity is independent of dense chunks and ECS entities | `VoxelMaterializationStore` is keyed by realization address; its entries independently retain activity, dense state, derived revision and optional surface. Disposable ECS manifestations are downstream. | **Strongly present.** Inactive dense entries still consume warm RAM until bounded cache eviction. |
| Prove uniform air/solid before allocating dense samples; keep uniform state compact | Every generation recipe calls `DenseVoxelMaterialization::generate`, which loops through the padded full sample lattice. Only after generation does it detect whether a surface transition exists. Uniform results avoid surface derivation and receive no presentation mesh, but the store retains the full `DenseVoxelMaterialization` sample arrays; no separate compact `UniformAir`/`UniformSolid` occupancy state or per-address pre-generation field classifier was found. Separately, demand traversal can prune whole regions using a spherical surface-shell test with a two-chunk margin. | **Not implemented as specified.** Coarse demand culling avoids scheduling much off-shell air, but it is not a compact occupancy fact for addresses still demanded, and it relies on the current sphere rather than authored conservative relief bounds. The source proves the dense allocation path, not its measured cost. |
| No presentation ECS entity without actual triangles | Manifestation membership requests presentation only for current surface caches with triangles; no-surface coverage is published without manufacturing a manifestation. | **Implemented structurally.** No ECS-count or rendering measurement was collected. |
| Collision and presentation are independently fulfilled; editing can be requested independently | Role masks and collision aggregation are separate from presentation membership; editing demand can publish from dense store data without a render surface. | **Represented in the source model.** Runtime correctness across all role combinations was not exercised. |
| Compact/batched voxel coverage; generic snapshot accepts non-entity facts | `UsfCapabilityCoveragePublication` is a batch component on each scale-realization entity; no-surface cells are sorted and published as facts, while actual surface manifestations publish entity-backed realization. | **Substantially implemented.** The current publisher emits one fact per active no-surface materialization; adjacent-cell cuboid coalescing and coverage-volume performance were not located/measured. |
| Capability-first, versioned priority tickets shared across all work stages | Demand ranking considers role, semantic priority, boundary focus, trajectory distance and observer distance. Generation compares worlds by each world's next-ranked pending chunk and re-ranks per round; within a world, pending chunks are a sorted `VecDeque`. Worker lanes provide critical/normal priority and weighted-fair service. | **Partially implemented with a different shape.** No global ticket heap/keyed revision state or cross-stage classify→dense→surface scheduler exists, and there is no classification stage. | Runtime/test evidence validates memory, entity count, backlog and collision | Two inline voxel source tests are present (region traversal and realization intent); no separate `spacetime-engine/tests` directory was found. This is a useful example of partial architectural adoption that a commit-count narrative would miss: the store split, real surface-only manifestation lifetime, batched compact coverage, role-aware ranking and fair worker lanes all exist, but the first promised compact-empty classification stage does not. Demand traversal does reject whole regions outside a sphere shell using a two-chunk margin; this can narrow requested voxels around the current spherical surface. It is a geometric demand filter, not a proof-bearing occupancy result, and it does not remove dense-array cost for addresses that survive traversal. It also needs a conservative terrain-envelope model before it can safely coexist with kilometer-scale relief. Current “sparse voxel” means **demand selection is region-culled and realization-keyed, ECS manifestation is surface-sparse, but dense storage for a generated no-surface address is still a full sample lattice.**

### 7d. The old world-generation scale atlas is not the current scale model

The archived [USF World Generation Scale Atlas](https://github.com/GHF-Studios/Loo-Cast/blob/020877577d1c1c0f86b69a519b43d5af2dcea844/spacetime-engine/USF_WORLDGEN_SCALE_ATLAS.md) is unusually explicit about its own status: “historical proposal, not a description of the live world.” It defines 36 non-negative spatial scales from S+35 down to S0 for a top-down generative chain, and explicitly says the broader 71-scale USF stack is not a noise pyramid. Its companion September 30 megapass begins from S+35, proposes a present-day cosmological bootstrap, recursively refines through each scale, then realizes local terrain. That is a proposed world-generation contract, not present behavior.

The current engine's numerical USF is instead 71 **spatial** slices, S−35 through S+35, with exponent meaning metres per native spatial unit ([spatial algebra](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/usf/mod.rs#L1), [runtime spatial stack](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/spatial/mod.rs#L1)). S0 is a unit convention, not a privileged origin. The current `worldgen` kernel has no `TemporalScale`, epoch-keyed phenomenon cache, 36-step evaluator, or generation chain; it supplies deterministic keyed sampling, exact/procedural constraints and a sparse index of authored construction facts. The only fixture consumer authors Earth and Moon as facts and uses the same body constructor. The current Moon orbit uses analytic elements and Bevy virtual elapsed time; that is not a temporal Scale Slice or coupled space-time coordinate.

The proposals also differ on time. The archived scale atlas calls spatial and temporal scale **orthogonal**, treating `TemporalScale` as a model-resolution label and fixing the first epoch. The October 9 spatial megapass later records an owner-directed future constraint: one authored scale index couples baseline spatial and temporal units by ×10 per step, with local clock-rate adjustments; canonical world time and event order must be designed before temporal slices are implemented ([plan, future constraints](/home/leslieghf/Vapor/Loo-Cast/docs/superpowers/plans/2026-10-09-usf-spatial-authority-megapass.md#future-constraints-not-current-implementation)). This newer direction supersedes the atlas's orthogonality as the owner's intended model, but does not supersede current implementation: the plan explicitly defers temporal slices, and the present source remains spatial-only.

| Question | Historical proposal | Current source / later direction |
|---|---|---|
| What does a scale number describe? | The worldgen atlas maps non-negative S+35…S0 to semantic generation domains and assumes traversal through each. | Current USF maps S−35…S+35 to spatial unit exponents; all are runtime spatial partitions. The atlas's domain chart is not wired into this stack. |
| Is temporal scale implemented? | The October 6 evaluator had an opaque temporal-resolution label and fixed bootstrap epoch; it was not a clock. | No temporal coordinate or temporal slice exists in current USF/worldgen source. Moon propagation reads Bevy virtual time. |
| How should spatial and temporal scales relate? | Atlas proposal: orthogonal; do not freeze a temporal exponent range. | Later owner direction: one coupled scale index, ×10 baseline space and time per step, with gameplay-local clock adjustment. Still future design. |
| Does worldgen produce the present Earth/Moon? | Atlas and September 30 design describe a desired top-down procedural route. | Fixture uses exact authored Earth/Moon facts, and the procedural constraint closures are unused. No cosmology-to-terrain chain or general terrain generator is present. |

The correct historical reading is a sequence of **three different models**, not one continuous implementation: a broad +35→0 generation proposal; a disconnected descriptive evaluator with an opaque temporal-resolution tag; and today's deliberately narrower authored-fact/provenance kernel. The later coupled-space-time direction is a fourth, owner-approved future constraint. The 71-slice spatial stack itself remains substantial architecture, but its existence does not make any of these world-generation or temporal contracts operational. See the [detailed scale-model crosswalk](loo-cast-vapor-semantic-diff-review.md#october-25-three-scale-models-worldgen-atlas-descriptive-evaluator-current-usf).

### 7e. Authored geometry and procedural presentation are real facilities, not yet complete lifecycle owners

The `.spacemap` path is one of the clearest current authoring slices in the engine: typed RON schema, validation, expansion cap, compiler IR, runtime meshes/colliders/lights/markers, and a playground adapter that interprets generic marker kinds. The data-to-runtime boundary is genuinely reusable. Its teardown is incomplete: asset removal is ignored, and generated manifestations are keyed to a raw source `Entity` without child/linked-spawn ownership. Removing the asset or despawning the scene source can leave stale generated entities. These are source-derived states, not runtime-reproduced. Focused compile and procedural-asset tests once existed but `e987230` deleted the current module tests. A further boundary is that the playground marker adapters are one-shot: watched map edits rebuild markers but do not reapply already-consumed spawn/portal positions. The `.spacemap` schema has no explicit version or integrated Vapor IDE editor; its README still describes editor support as future work. See the [detailed audit](loo-cast-vapor-semantic-diff-review.md#october-25--authored-geometry-and-procedural-assets-reusable-pipeline-incomplete-lifecycle-and-recipe-authority).

`ProceduralPresentationAssets` is broader than its current consumer set. The debug-grid marker is consumed; cracked-clay, star, planet and lunar asset handles currently have no source consumer. The 256×128 planet texture's “tectonic/biome” look is presentation-only and does not change the spherical celestial field. The mutable reflected cracked-clay recipe regenerates synchronously in Update without an input/resolution cap; pathological values can make that one update expensive. These are present architecture and budget gaps, not claims of observed stutter.

This complements the worldgen crosswalk: the current seed/provenance + exact Earth/Moon facts are an intentional smaller construction substrate, not the September 30 generator graph or an operational procedural planet model. Full evidence, line anchors and the deleted-test history are in the [semantic review](loo-cast-vapor-semantic-diff-review.md#october-25--authored-geometry-and-procedural-assets-reusable-pipeline-incomplete-lifecycle-and-recipe-authority). No build, test or runtime file-watcher/teardown check was performed.

### Configuration is layered for voxel policy, not a global engine policy surface

The engine has a coherent compiled-default → engine-root RON → transient typed-override chain; Vapor's launch path supplies the engine root explicitly, avoiding a Steam-working-directory assumption. Valid file reloads retain runtime overrides, and invalid candidates retain the last valid effective config. The effective root model currently contains voxel policy only. Console runtime-variable registration exposes five of its seven override fields; the other two remain RON/programmatic-only in the inspected code. Tests check path selection only. The Oct 8 flattening of nested voxel configuration is a useful organizational simplification, but it did not create an engine-wide settings registry. See the [source trace](loo-cast-vapor-semantic-diff-review.md#october-25--configuration-a-sound-precedence-chain-with-a-narrow-domain-surface).

`ReconstructibleFrameBudget` is a shared cooperative pacing hint, not a frame-time guarantee: its overshoot debt uses wall-clock spacing between `First` stages (including waits/render cadence), and it cannot preempt work. It admits one initial unit per class even after allowance is spent. Its single `Publication` estimate mixes inexpensive bookkeeping with potentially expensive mesh construction, and the mesh-rebuild caller never closes its token, so mesh duration does not train that estimate. The loop still has a separate configured iteration cap; no runtime hitch is claimed. See the [caller-by-caller audit](loo-cast-vapor-semantic-diff-review.md#reconstructible-work-is-a-soft-admission-heuristic-with-one-unclosed-measurement-path).

### 8. Registry, Identity and Platform Server

**Registry exists, but its implemented record model is still source-topology/provider discovery, not the full content/release authority envisioned by the owner.** Its live API exposes health, status, ecosystem/repository facts, and provider-account/repository facts. Types model these same records; the SQLite database seeds official ecosystem data. The inspected API has no route/data model for content versions, typed pack graph, signed artifact records, Workshop type enforcement, install receipts, compatibility solving, or release provenance ([routes](/home/leslieghf/Vapor/Vapor-Platform-Server/Vapor-Registry-Server/src/main.rs#L51), [types](/home/leslieghf/Vapor/Vapor-Platform-Server/Vapor-Registry-Server/src/types.rs#L1), [README](/home/leslieghf/Vapor/Vapor-Platform-Server/Vapor-Registry-Server/README.md#L1)). This Registry is not unused: the shared `vapor_core::RegistryClient` reads its ecosystem endpoint to acquire registered repositories into a Superworkspace ([client](/home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/registry.rs#L50), [acquisition](/home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/ecosystem.rs#L86)). That is meaningful bootstrap/topology authority; it does not make it the Workshop content catalog.

The SQLite Registry is currently a **source-seeded read model**, not an operator-editable catalogue: process startup upserts six official repository records from constants and deletes/recreates the three top-level membership rows; HTTP exposes only GET routes. The latest seed change (`566130c`, Sep 15) explicitly added Loo-Cast as a top-level acquired source root alongside the two container roots. Thus a database exists and supports durable reads, but source code remains authority for the official topology and manual DB edits to membership are overwritten on restart. [Detailed seeded-catalog review](loo-cast-vapor-semantic-diff-review.md#october-25-registrys-database-is-a-seeded-snapshot-not-an-administrable-catalog).

The bootstrap feed is also a source-acquisition trust boundary. The shipped root manifest currently points to the HTTPS Registry endpoint, and the client checks schema version, requested ecosystem ID, provider label, repository kind, and a one-component checkout path. However, the generic Registry client accepts either HTTP or HTTPS; the ecosystem response does not carry the provider account's `verified` bit; and acquisition clones the returned `clone_url` without checking that its host/owner agree with the claimed GitHub provider/repository identity ([configured endpoint](/home/leslieghf/Vapor/Vapor-Client/Vapor-Client.vapor.toml#L6), [URL policy](/home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/registry.rs#L52), [repo validation](/home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/ecosystem.rs#L341), [clone use](/home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/ecosystem.rs#L409), [provider verification seed](/home/leslieghf/Vapor/Vapor-Platform-Server/Vapor-Registry-Server/src/db.rs#L129)). The checked-in first-party endpoint is HTTPS and the server seeds fixed GitHub URLs, so this is a source-level trust-hardening gap, not evidence of a compromised endpoint or observed unsafe clone.

There is also a narrow CWD fallback: `load_bootstrap` first reads the installed app's `metadata/ecosystem.toml`, then walks upward from the service process's current directory looking for the source-root distribution manifest. The Registry discovery action receives an installation, not the user-selected workspace path. The fallback may be useful for a source-launched developer tool, but it is not tied to an explicit selected workspace in this call path; if the installed receipt is absent, behavior depends on whichever client first established the service process's working directory. This is conditional on missing installed metadata and has not been reproduced ([bootstrap fallback](/home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_core/src/ecosystem.rs#L172), [service discovery action](/home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_service/src/session/workspace.rs#L684)).

Identity owns Steam/GitHub identity, profiles, sessions, roles and authorization, and explicitly separates Vapor authorization from Steam publishing authority ([Identity](/home/leslieghf/Vapor/Vapor-Platform-Server/Vapor-Identity-Server/README.md#L1)). At the October 25 source snapshot it is a functioning identity and role-administration service: Steam OpenID browser login, Steam ticket verification, GitHub browser/device/token verification, SQLite-backed profile linking, hashed opaque session tokens, short-lived dashboard sessions, and role/audit operations are present. It does **not** yet expose the audience-bound cross-service introspection/authorization route described by the accepted contract; the registered routes stop at authentication/status/admin/profile/export and browser login/dashboard ([routes](/home/leslieghf/Vapor/Vapor-Platform-Server/Vapor-Identity-Server/src/main.rs#L63), [target contract](/home/leslieghf/Vapor/Vapor-Platform-Server/docs/cross-service-authorization-contract.md#L1)). Consequently Identity's “authorization source” currently means authority inside its own dashboard/admin handlers, not a capability all services can ask it to validate.

Content identity has a separate lexical seam: the shared `VaporId` constructor rejects only empty text and whitespace, while source discovery rejects manifest-side IDs and derives them from constrained source-root/local names ([shared identity](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_content/src/identity.rs#L13-L25>), [source-manifest parser](</home/leslieghf/Vapor/Vapor-Client/Vapor/crates/vapor_client_provider/src/manifest.rs#L343-L390>)). The current session APIs are specifically oriented to root-dashboard access: `/v1/auth/session/start` accepts only the `root-dashboard` purpose, and finish issues its cookie only for a linked Steam+GitHub profile with `root`. The security primitives are narrower and more concrete than one README bullet suggests. The checked-in VPS bootstrap sets it true, but the live deployed environment was not inspected. Consumption is a separate unconditional update rather than an atomic one-time claim. This is a source-visible replay/concurrency window if the same valid callback is submitted concurrently; no exploit or runtime reproduction was performed, and the unguessable state plus external provider verification still constrain the preconditions ([cookie/config](/home/leslieghf/Vapor/Vapor-Platform-Server/Vapor-Identity-Server/src/util.rs#L46), [attempt storage](/home/leslieghf/Vapor/Vapor-Platform-Server/Vapor-Identity-Server/src/auth_attempts.rs#L36), [Steam callback](/home/leslieghf/Vapor/Vapor-Platform-Server/Vapor-Identity-Server/src/browser_handlers.rs#L77), [GitHub callback](/home/leslieghf/Vapor/Vapor-Platform-Server/Vapor-Identity-Server/src/browser_handlers.rs#L208)). ### 9. Rhai, Rust generation, and code ownership

The in-game workbench is more than a syntax editor. `DeveloperScriptWorkbench` constructs a Rhai Engine, loads authored `.rhai` files, and supplies a default `debug.freecam.speed` document. `ScriptDocument::compile_candidate` parses the buffer; for that target it also calls `transform(preview_input)` and rejects a non-finite result. Commit promotes only a candidate matching the exact current buffer to the committed AST. At runtime, `transform_live_scalar` calls that committed function only when the document’s `live_enabled` flag is true; otherwise it returns the original value. The current integration therefore proves one real, target-specific, scalar execution path with edit/compile/preview/commit/revert state, not general hook invocation. Sources: [workspace/runtime path](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/devtools/script_workbench/workspace.rs#L18), [compile/commit lifecycle](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/devtools/script_workbench/document.rs#L145), [function validation](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/devtools/script_workbench/document.rs#L210), [live call site](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/devtools/script_workbench/workspace.rs#L94).

The host sets operation, recursion, expression, variable, function, module, string, array and map limits and rate-limits script logs ([host configuration](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/devtools/script_workbench/host.rs#L9)). It starts with `Engine::new()`, which includes Rhai’s StandardPackage and ordinary math functions; it then registers project helpers and log functions. So “bounded host” is supported; “minimal native environment,” a complete security sandbox, or user-defined capability graph is not. The freecam target’s `transform(f64) -> f64` is a bespoke host contract, and the scratch target is compile-only. The workbench code reviewed here has no typed schedule/phase, caller identity/cardinality/signature model, capability-context composition, retained-data/reacquisition lifecycle, Rust code generation, dynamic Rust/WASM loader, or unload transaction.

The runtime binding is narrower still: freecam movement calls the script once to transform the configured speed, then clamps the result to `[0, 1e9]` m/s and multiplies by boost and delta time ([freecam consumer](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/game/player/camera/freecam/movement.rs#L90)). The UI's Live checkbox defaults off on each newly loaded document, and the script console exposes status/compile/commit/revert/save but no equivalent live-toggle command. The enable state is not part of the saved script source or committed AST. This makes “runtime implementation” accurate, but “persistent live policy” inaccurate.

Script storage is also a host-owned filesystem lifecycle rather than a capability graph. The workbench materializes the current build's embedded defaults on startup, seeds missing files into a separate live tree, scans at most 256 `.rhai` files, and keeps existing live files across default updates. Root selection uses both environment overrides only when both are set; otherwise it walks upward from the process working directory for a Loo-Cast checkout, then falls back to the executable directory for deployed runs. Paths reject absolute paths and lexical traversal, but writes do not canonicalize/check symlink containment; scan/read failures are skipped rather than reported per file, and there is no source-file byte cap before compile. These are concrete implementation boundaries, not a claim of an exploitable vulnerability in the intended developer-owned local workspace ([storage](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/devtools/script_workbench/storage.rs#L1), [workbench bootstrap](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/devtools/script_workbench/workspace.rs#L26)).

The build-to-runtime handoff is now directly traced: `spacetime-engine/build.rs` recursively embeds every non-hidden-directory `.rhai` file below repository `scripts/` as source strings in a generated Rust table, sorted by logical path, with a 1,024-file build limit. Runtime writes the full table into `script-defaults`, then copies only missing files into `scripts`; an existing live file is preserved until explicit Reset Default. The two current sources are `debug/freecam_speed.rhai` and `scratch/experiment.rhai`; the README says only the former has a live host policy and the other is compile-only. The Engine crate owns the build script, while `loo-cast-game` depends on that crate, so this package path embeds scripts through the Engine dependency rather than a separate game-side loader. This is source embedding, not Rhai-to-Rust generation or a compiled Rhai AST. One concrete budget mismatch is visible: build-time collection allows up to 1,024 files, but runtime discovery stops at 256; the current two-file tree does not hit it. Runtime collection also does not sort directory entries, so behavior at that cap may be order-dependent. [Build script](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/build.rs#L15), [runtime materialization and missing-only seeding](/home/leslieghf/Vapor/Loo-Cast/spacetime-engine/src/devtools/script_workbench/storage.rs#L118), [script-source contract](/home/leslieghf/Vapor/Loo-Cast/scripts/README.md#L1), [Game's Engine dependency](/home/leslieghf/Vapor/Loo-Cast/loo-cast-game/Cargo.toml#L11).

Vapor-GUI adds another, separate level: its Rhai semantic projection supplies lexical/object navigation, and the IDE parser compiles for diagnostics without executing the AST. This does not share the in-game workbench’s runtime engine, script target, committed AST or diagnostics state. The detailed GUI/editor cross-check records those boundaries ([semantic IDE trace](loo-cast-vapor-semantic-diff-review.md#cross-repository-hunk-supplement--semantic-ide-becomes-a-workbench-october-23-2026)).

This narrows the roadmap contradiction. The sentence “No Rhai parser, executor, or capability implementation exists” is false for parser and executor if it means any Rhai execution; it remains directionally true only for the not-yet-evidenced owner-designed callable capability system. The ambiguity is partly in the roadmap vocabulary: “capability” does not identify whether it means the small registered host functions, spatial realized-coverage components, or the proposed typed/scoped invocation graph. The roadmap should inventory those separately, not say Rhai itself has yet to begin ([roadmap claim](https://github.com/GHF-Studios/Vapor/blob/main/docs/roadmap/07-packs-capability-rhai-runtime/03-capability-rhai-runtime/README.md#L5)). These facts do not establish that advanced scripting design has landed.

Earlier owner discussion specifies typed schedule and phase, caller identity/cardinality/signatures, context-specific capability graph/handles, retain data then reacquire access, recursive evaluation layers, static immutable core, and dynamic/unloadable Layer 3 Rust WASM. This is **historical owner direction requiring explicit design merge**, not current implementation evidence. Editor/runtime Rhai support is not evidence for generated Rust, dynamic Rust/WASM lifecycle, capability graph reconfiguration, or sandbox guarantees. A pinned Rust toolchain gives reproducibility, not sandboxing: Cargo build scripts and proc macros can execute host code.

### Why the latest snapshot's problems compound

The current defects are not independent checklist items. The high-risk path crosses several owners, and each boundary transforms or narrows the state that the next boundary receives:

1. **Authored declaration → candidate:** role-specific TOML becomes a common AuthoredContent, then a provider-neutral ContentCandidate. Identity/kind/version/dependencies survive, but the reference model uses a string relationship plus optional flag; conflicts, Workshop provenance, runtime payload and source status live elsewhere. Manifest containment protects the marker file, but the later generic package copier follows symlinks in the project tree, so it does not inherit that root boundary.
2. **Candidate → resolved selection:** the resolver selects required edges and exact versions, but skips optional edges and does not return a selection/choice record. Per-edge “latest matching” is not a graph-wide constraint solve. Thus compatibility alternatives and selected members cannot reliably be reused by later projections.
3. **Selection → local Library:** install/catalog projections combine source, Workshop, cache and install observations. The current Library projection can drop authored conflicts; ownership traversal follows required edges but is keyed by stable ID rather than exact version. The resolver graph is therefore not preserved as one complete semantic object through the Library.
4. **Packagepack → local install state:** owner direction already makes Packagepack the one playable-selection identity and “composition” an informal synonym. Current source still persists a distinct Composition model and active ID, initially `"default"`. The unresolved seam is which exact-version resolution, launch preferences, installation receipt, update policy and draft/fork state belong in local per-user state around the Packagepack—not whether a second content identity should remain.
5. **Local intent → Steam side effect:** subscription and download happen through Steam, while owner/policy/install state persists locally. A partial Steam batch can alter the account while Vapor skips projection refresh; Auto-Install enable reaches an accepted UI/action path but real-service dispatch rejects it; cache mutation can activate replacement before a later receipt/cleanup error is returned.
6. **Operation request → user-visible progress:** owner direction calls for frontends to submit actions to the shared service and queue requests whenever they can safely wait; only incompatible actions should be refused. Protocol labels some conflicts queueable and has a Queued phase, but the service rejects reservation conflicts. Workshop acquisition is sequential and has no item-level progress, while snapshots repeat filesystem discovery. The policy direction is settled; queue fairness, persistence, cancellation, resource keys and progress semantics remain implementation/design details.
7. **Current behavior → docs/product surfaces:** books, CLI help, UI labels, Registry topology and server operating docs were written against different stages of this model. Users can be taught a Composition model the owner has since collapsed into Packagepack, see a feature described as absent despite existing code, or receive “update needed” for a broader set of launch-plan failures.

This chain explains the apparent “exponential” scope: a changed edge contract affects authored manifests, resolution, install planning, Library projection, Auto-Install retention, Workshop acquisition, composition identity, UI filters, IDE inspectors, release artifacts, docs, and recovery. The correct unit of analysis is therefore the **semantic handoff**—what identity and evidence enter a stage, what is preserved or discarded, who owns side effects, and how a later stage can reconcile failure—not the isolated file or feature. This is an architectural interpretation supported by the traces above; it is not proof that every incident has the same cause.

### 7d. Role selection and tool provisioning are coupled more tightly than operation requirements
